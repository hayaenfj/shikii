# Connection example: the Claude Code and Codex hooks (`shikii hook`) — measuring the AI's own thinking at two points, before it thinks and after it has finished

Business decisions (routing inquiries and so on) are called by the agent over MCP ([mcp.md](mcp.md)). Separately, these hooks connect **recording conversations, looking up memory, and judging the AI's own thinking** to shikii. There are only two moments it measures: before thinking after receiving the person's request, and when closing the turn after thinking. The Claude Code / Codex hooks start recording. The new-format pre-work decision is called by the usual agent that received the notice, after it has sorted out the context.

No decision is made per tool call (right before Bash or Edit); the hook that runs there (0.11) only delivers a lesson naming that file or command, and refuses a command only when a `forbidden-commands` guard the person enabled says so. Classifying each command is not the AI's thinking but noise from the work; it runs dozens of times per request and drowns the request-level decisions (measured: 4606 command decisions against 84 request decisions). Whether something is allowed is already covered by Claude Code's permission and deny rules.

**The Claude Code and Codex hooks** (both have hooks of the same shape; `install` writes to both settings). OpenCode gets MCP and the skill through `shikii init`, but has no entry point that measures thinking automatically (to add one, see "Adding it to other agents" below). The words for bands (act / ask / discard / abstain), lines (calibration) and receipts are in [bands.md](../skills/shikii/references/bands.md).

It measures 4 things (the specs are in [`claude-code/specs/`](claude-code/specs/)). The first 2 are forecasts, the last 2 are self-evaluations:

| spec | when | question | who records and checks |
|---|---|---|---|
| `prompt-kind` | before thinking (UserPromptSubmit) | what will the AI end up doing for this request (edit / explain / investigate / run / decide) | **automatically from the outcome**: when the next request arrives (or at the end of the turn if none), edit if the working tree's contents changed, !edit if not (a partial truth "it was not edit", weight 0.7). A !edit at the end of a turn is carried over to the person's next request, and if background work changes things later (Stop after a notification), the same decision gets edit instead (the newer truth wins) |
| `needs-plan` | before starting (notice from UserPromptSubmit) | should the AI that received this request have checked with the person before starting work (was something about the approach or scope left for the person to decide) | the usual AI sorts out what was agreed and what is open, with the original text, and the person answers on the page |
| `changes-in-scope` | after thinking (Stop) | were the files changed in this turn (the list from comparing the working tree at request time with now) within the request's scope. Not asked if nothing changed | the AI scores provisionally with grounds, and the person checks samples and held items. Separate from truths and calibration |
| `done-as-asked` | after thinking (Stop) | looking at the request, the changed files and the final reply, did it finish what was asked (is nothing left for the person to say again) | the AI scores provisionally with grounds, and the person checks samples and held items. Separate from truths and calibration |

There are 3 to 4 decisions per request (independent of the number of tool calls). `status`'s "human decisions per 1000 decisions" goes down the more you use it, and act decisions carry a receipt (how many a person checked and the precision). These are numbers for running the decision model, kept separate from the record of conversation memory helping or the rate at which corrections went down.

**Conversations, scores and lines are all per project.** Each project enabled with `shikii --init` has `decisions/` `wiki/` `guards/` `records/` `labels/` `sessions/` `handoff/` in its `.shikii/` (`handoff/` is the work records: files you keep rewriting as you go, such as audit reports, release steps, diffs and images). Initialization prepares them, and the hooks do the recording afterwards. Inside Git the unit of work is the repository root; outside, it is the cwd. Different folders with the same name are not mixed, and subdirectories and symlinks of the same repo are the same work. Do not use a link from `.shikii/` to a shared place. The hook adds `/.shikii/` to Git's local `info/exclude`, so private conversations are not swept into `git add -A`. Taking the state also excludes `.shikii/`, so shikii's own records are not counted as file changes.

`~/.shikii/agent` holds the shared types, tools and project index, and each project's page marker (`pages/<id>.json`: port and pid). There is one page per project; the hook of the first request starts it on a free port (`serve --store <project>/.shikii --port 0`) and opens it in the browser. The shared entry (`serve --store ~/.shikii/agent --port 8096`), only when you start it by hand, reads each work's records from `/p/<hash of the real path>/`. The API under the same URL also saves scores, truths and lessons to that work, and does not add up results. The answer link the hook shows opens that work directly too. Conversations and lines in the old shared store are not carried over automatically.

## Sorting out the context before starting

The new-format `needs-plan` takes the current request, the agreed approach and the open questions as input. The hook saves the current request and the previous exchanges of the same session, and points the usual agent to `shikii hook plan query / submit`. The person does not fill in fields, and no other model is needed. The agent sorts it out with quotes from the original text, and marks unknown items as unknown. The page also shows the request, the agreed approach and the open questions separately. How to choose the purpose and context is in the English skill for agents; the program returns the original text of the latest 4 items of the same session and the wiki matching the search words the agent specified. It has no logic that guesses search words to decide the approach. The wiki is quoted after checking sources and versions, kept distinct from this request's agreement.

An agreement needs grounds in something the person said; a plan the AI only proposed is not an agreement. Even if a quote exists, the meaning of the summary is a hypothesis and is not permission to act or a human truth. When both items are unknown, the decision is skipped. While there is no line, it only records the prediction and gives no advice to check based on it. If the request moved on while waiting for the model, the old result is not recorded. Resending the same summary keeps the first decision. [JSON and the rules for grounds](../skills/shikii/references/planning.md).

Questions in existing projects are not rewritten automatically. In the new format, past truths whose agreed and open inputs are missing are not reused; answers to the new inputs are collected.

## Using everyday conversation for the next request

Just saying "it's not finished yet" or "I didn't ask for that" as usual keeps the original request, the AI's final reply and the person's message after it as one set. When a similar request comes next, up to 2 lessons from the same project whose title and conditions are close are quoted briefly to the AI before it starts. For a topic with no lesson, it returns up to 1 similar unsorted conversation. The person's own answers on the page to the hook questions for similar earlier requests are quoted too (key `decision:<trace_id>`, the earlier request and what the person answered in the page's words); one fitting answer keeps one of the 2 seats. No answering on the page and no other model is needed, and this lookup works while the decision model has no line and while the model is stopped.

What is recorded is the original text (request, reply and next message, up to 1500 bytes each), not something a machine decided is a correction or an additional request. "Also translate it into English" is kept in a form that can be read as an additional request, and the absence of a message is not counted as success. The interpretation of the conversation is not put into truth labels or accuracy numbers. The current request and rules take priority over the quotes.

Records are in `.shikii/records/feedback/<hash of the project's real path>.jsonl`. They are separate from the usual decisions and truths; saving and searching are local, and quotes are passed to the context of the coding agent in use. They are not sent to another decision model or the proposer. Conversations of a different repo with the same name are not mixed, and subdirectories and symlinks of the same repo are looked up as the same work. A request and the next message are linked only after a reply in the same session and the same work. Notifications, subagents and additions before the reply are not linked. It reads up to the latest 256 items within the last 4 MB, and searches by the overlap of the request's words. The memory passed is wrapped as JSON, up to 1800 bytes in all after escaping. The same version is not repeated to the same session for an hour, and an updated version is delivered right away.

In 0.4, when 2 conversations are pending for scoring and wiki summary, or on a request after one has waited a day, it passes only a short reflection notice and the source IDs. The agent checks the original text, scoring targets, existing lessons and the person's correction examples at once with `shikii_reflect` or `shikii reflect query / submit`, and saves them together. The original text is not piled into the notice. If there is no lesson to reuse, it can be marked sorted with the source IDs only. Even for sessions whose MCP is not updated yet, the hook points to the CLI by the executable's absolute path.

The generated area is `.shikii/wiki/lessons/<hash of the work>/`. `index.md` is the index, `log.md` the history of additions, `revisions/` the earlier versions. Source material stays unchanged in `records/wiki-sources/<hash of the work>/`. Passing a lesson's `id` updates it, and `replaces` replaces old lessons. Lessons whose sources disappeared or changed are dropped from lookup. Lessons are always hypotheses and do not change truths, lines or the state of `patterns/`.

Read lessons and sources with `query`, and check sources, versions and links with `lint`. Stop also checks once a day and repairs drift in the index. Merging into and updating existing lessons comes first (there is no fixed upper limit on the count; removed in 0.5.0). Automatic memory does not pile already-sorted original text onto lessons. Quotes go to the agent in use and are not sent to a new model. The "Knowledge" page shows the lessons and original text of the selected work.

## Observing delivered memories and corrections

The quotes and versions actually delivered are tied to the request ID, and the decisions they were used for and the check results are saved in the usual reflect. How a memory helped is helpful / unused / harmful / unknown. Correction tracking from 0.4.1 attaches the original text of the person's reply and the next action given in the lesson's `correction: {source_id, quote, action}`, and records followed / repeated / not_applicable / unknown in `correction_result` the next time it is delivered. The reading as a correction stays a hypothesis, and no truth or permission to act is made from the existence of the original text.

Following a correction and being helpful are separate observations. Success or silence alone is not counted as improvement; unknown and unevaluated are kept. The numbers on the Knowledge page are results within the window of recent deliveries, not an improvement rate against no memory. No extra model or human input is needed; it is handled with the existing `reflect query / submit` and MCP / HTTP. [JSON and the rules for grounds](../skills/shikii/references/review.md). Correction tracking is available from 0.4.1.

## Installing and removing

```sh
curl -fsSL https://raw.githubusercontent.com/hayaenfj/shikii/main/install.sh | sh
shikii hook install          # only shows what it would do (the same as install.sh runs with --yes)
shikii hook install --yes    # do it. Takes effect when you restart claude in a new terminal
shikii hook uninstall --yes  # removes only the hooks it added (6 for Claude Code, 3 for Codex). Each project's records and truths (.shikii/) stay
which shikii                 # Claude Code calls `shikii` as is, so it needs to be on PATH
```

**After installing, initialize once in each project you use.** Run `shikii --init`, or ask the agent "I want to use shikii in this project". Initialization sets up the ready-made questions (the hooks' 4 and the wiki's 2), the wiki, MCP, the rules and the entry to the page, and finally saves `.shikii/project.json`. With no marker, another project's marker or a broken marker, the hooks do not run and touch neither the store, Git's exclude nor starting the model. A failed initialization does not enable it, and running it again keeps existing data. With no key, if the model (:8080) does not answer, the hook right after the request starts `shikii up` in the background (the first time it downloads the model, so a few turns in between simply get no records; if there is no llama-server, one line in hook.log says how to install it). There is one answer page per project; if it is not up, the first request's hook starts `shikii serve --store <project>/.shikii --port 0` in the background (the hook does not wait; serve takes a free port, writes a marker to `~/.shikii/agent/pages/<id>.json` and opens it once in the browser). The right to start is taken by only one hook through a flock on a marker (`starting-model` / `starting-page-<id>`), and it does not start while the child started earlier is alive, nor within 10 minutes for the model or 30 seconds for the page. Output goes to `~/.shikii/agent/up.log` and `serve-<id>.log`.

What `install` does (a second run adds nothing):

1. Puts the shared types and the ready-made wiki in `~/.shikii/agent/`. Each work's `.shikii/` is prepared by `shikii --init` (same as `shikii init`), which copies the 4 specs from the embedded originals, **only the missing ones**. Other works' lines are not copied, and specs already grown in that work are not touched. It puts the agent's rules (the skill) in `~/.claude/skills/shikii` again (the same thing as `shikii init`; with this the agent can also set up business decisions). If llama-server exists, it starts the model in the background
2. Adds 3 to the `hooks` of `~/.claude/settings.json` (Claude Code) and `~/.codex/hooks.json` (Codex), `UserPromptSubmit`, `Stop` and `SessionStart` (0.11; the project's brief at the start and right after a summary), and 3 more for Claude Code only: `SubagentStart` (0.7.3; delivers lessons in the same way when a subagent starts), `PreToolUse` for `Agent|Task` only (0.9.1; saves the task text passed to the child, outputs nothing and does not stop the tool) and `PreToolUse` for `Edit|Write|MultiEdit|NotebookEdit|Bash` (0.11, `hook tool-lesson`; right before a file edit or a command, at most 1 lesson that names that file or command, as context only, and refuses a command only for a forbidden-commands guard the person enabled) (none is added to Codex: Codex has no SubagentStart, and its PreToolUse could not be shown to pass context to the model, so `~/.codex/hooks.json` changes with `SessionStart`, so Codex users trust the hooks again with `/hooks`) (the command is **the executable's absolute path** + ` hook <event>`. It works even if `shikii` is not on the PATH of the agent's shell. If you move the executable, run `shikii hook install --yes` again and the handlers with the old path are removed and new ones added. Timeouts are 15 seconds for UserPromptSubmit, SubagentStart and PreToolUse, and 20 seconds for Stop. Codex asks to trust its hooks again whenever `~/.codex/hooks.json` changes (a new path or timeout); until you trust them with `/hooks`, Codex skips them, and `codex exec` says nothing. The only matchers are PreToolUse's `Agent|Task` and `Edit|Write|MultiEdit|NotebookEdit|Bash`). It removes the shikii `PreToolUse` hook added by old versions (`hook pre-tool-use`) (other hooks and keys stay). Codex makes the person confirm new hooks once: open `/hooks` in Codex and trust it (otherwise the hooks are skipped). The first time it touches settings.json (install or uninstall), it saves the content just before, without shikii's hooks, to `settings.json.bak-shikii` (only once. If there was no settings.json to begin with, it does not create one, and it does not back up a settings.json that install created)

Fixed rules (there are no options): the store is each work's `.shikii/` (decisions/ wiki/ guards/ records/ labels/ sessions/ handoff/); the recommended model is TypeSafe's Jev (when the environment variable `TYPESAFE_API_KEY` is set; local with `SHIKII_MODEL=local`), and without a key the local `http://127.0.0.1:8080` (`shikii up`); the answer page is on a free port per project (`shikii page` tells you). The default when you start `serve` by hand is 8095. Every ready-made spec is `send_to: [hosted, local]`, `pii: false`, and with a key the requests, replies and wiki lessons are sent to TypeSafe (the decision of 2026-10-23; they also stay in the local records). One decision takes about 0.2 seconds on Jev and 0.1 to 0.6 seconds on the local model (the 2 questions run in parallel), and one hook run (including startup and recording) 0.6 to 1 second. That is only added once right after the request and once at the end of the turn; a tool call gets only a lesson naming its file or command, or an enabled forbidden-commands guard's refusal. Without a model, it stays silent without waiting.

The hooks start the answer page. To start it by hand:

```sh
shikii serve --store <project>/.shikii --port 0 --local http://127.0.0.1:8080   # the first request's hook starts it. The port is a free one, the marker is ~/.shikii/agent/pages/<id>.json
```

## The shadow period → acting by band

shikii does not give `act` while there is no line (calibration). Advice based on decisions also waits until a line is drawn. Past conversations can be returned as quotes without judging right or wrong, so they reach the agent before it starts even while there is no line. It never stops a tool, except that a `forbidden-commands` guard the person enabled refuses a command right before it runs (0.11). At the end of a turn, one line "N waiting for your answer → URL" appears (below).

**Trying ways of asking is also done by the machine** (the counterpart of the wiki's lint, on a slow cycle): when a spec has `variants:` (candidate wordings a person wrote), human truths are at or above `eval.min_n`, and truths have grown by 50 since the last automatic tune, Stop runs `shikii tune` (without `--write`) in a detached separate process, and leaves the result in `wiki/runs/` and in the `auto-tune …` line of `hook.log`. For a spec with no candidates it does nothing (nothing to try). For a candidate that did better, before the next request the hook asks the agent once to check whether the meaning is the same and (when the setting is not English) to translate both (`shikii hook variants check`). If the same, it is adopted and calibrated on the spot, and Stop tells the person with the translations ("keep it / revert" on the page). When it cannot decide, it asks the person with the translations and the difference, and when different it is not adopted. It can also be adopted with `tune --write` in the terminal or "the meaning is the same" on the page. The last count is saved in `tuned-<spec>`. A person can write candidates in their own words in the "Ways of asking" section of the page (a short name and a rewording of the question; for a choice, also the option descriptions as "id: description" lines). Sending it, `POST /v1/tune/variant` validates it as a spec and then adds it to `variants:` (it neither scores nor adopts). Without opening the YAML, the cycle runs on the page: a person writes → the machine measures every 50 → the agent checks the meaning and adopts, and the person can revert.

The machine draws the line: when human truths (1 per input; answering the same request text 50 times is still 1) reach `eval.min_n` (50), the line is drawn and written into the spec, by that serve right after answering on the page (`serve`), or otherwise by the hook at the end of the next turn (for all 4 specs; prompt-kind's outcome truths do not go through the page, so this is the only place they can be drawn). The hook starts `shikii calibrate --write` in a detached separate process (so a long re-asking after changing wording does not hit the hook's timeout; at most once every 10 minutes per spec). The result is the `auto-calibrate …` line in `hook.log`. From there the hook changes how it behaves.

| spec | decision | what the hook outputs |
|---|---|---|
| any | no line (shadow) | no advice from the decision (quotes of past conversations are separate) |
| needs-plan | act | context to the agent `shikii: this request looks like one to agree on an approach with the user before changing anything (needs-plan p=0.88; line on 61 truths, human-checked precision 0.96). Consider EnterPlanMode or a one-line confirmation first` |
| needs-plan | discard (no need to agree) | nothing |
| changes-in-scope | discard (confident it was "out of scope") | one line to the person at the terminal `shikii: the changes this time look outside what you asked for ("Were the changed files all needed?": the AI is 88% sure…). Check the changed files before going on` |
| done-as-asked | discard (confident it was "not finished") | one line to the person at the terminal `shikii: what you asked looks unfinished this time ("Did it finish what was asked?": the AI is 85% sure…). Something may be left to ask for again` |
| changes-in-scope / done-as-asked | act (in scope / finished) | nothing |
| needs-plan | ask (there is a line but it was unsure) | one line at the terminal `shikii: the AI is unsure about "Should it have asked you first?" (leaning to "yes"). Answer later: http://127.0.0.1:<the free port>/?spec=needs-plan&trace=…` |
| changes-in-scope / done-as-asked | ask | passed to the AI's provisional scoring in the next conversation. The person checks samples and held items |
| prompt-kind | anything | nothing (it saves the tree's hash for the outcome truth) |
| (Stop) | even with no line | if decisions newly started waiting for an answer, one line (count and URL). Otherwise silent |

**It does not stop tools, and gives a permission decision (allow / ask / deny) only when a `forbidden-commands` guard the person enabled refuses a command right before it runs (permissionDecision deny, 0.11).** The question before thinking (needs-plan) becomes context for the agent, and the questions after thinking become text for the person at the terminal: returning context at Stop makes the conversation continue on its own, so whether to continue ("it's not finished yet") is up to the person. The hook outputs one of 5 things: "silence / context to the agent / one line to the person / only when a guard is hit, stopping Stop with the reason (decision: block) / an enabled forbidden-commands guard refusing a command right before it runs (permissionDecision deny)".

The text is in English. If `language` in `~/.claude/settings.json` is Japanese, the same text is also given in Japanese. For other languages the text stays English, and the record's `display` holds only the language plus, if present, the question and answer names from the spec's `display.<lang>`. The lines for the person name the question by its title on the page and give the AI's confidence as a percent, not the spec id or p (the context for the agent keeps them). Example: under `shikii: what you asked looks unfinished this time ("Did it finish what was asked?": the AI is 85% sure)` comes `shikii: 今回は頼んだことを終えていないように見えます(問い「頼まれたことを終えたか」、AI の自信 85%)`. The record (`records/<spec>.jsonl`) also keeps the language, question, answer and the text shown as `display`, so you can trace afterwards "what it was told and what it did". For yes / no questions (noul), the answer name is the "no" side (not finished, out of scope) when p(yes) is below 0.5. With an English setting it is English only, and there is no `display` (also none when the spec has no `display.<lang>` and no text was shown).

At the end of the turn (Stop), if the decisions of that session waiting for the person's answer (unsure decisions, and a sample of 1 in 20 act decisions; while there is no line, decisions whose raw probability is at or above the spec's `thresholds.ask` are "unsure", and discards below it are only recorded) have newly grown, it outputs just one line: `shikii: 3 of this session's decisions wait for your answer: http://127.0.0.1:<the free port>/`. The line has the URL of that project's page; if it is not up, the hook starts it in the background and writes "not up yet". The same count is not repeated every turn. Opening with `?spec=<id>&trace=<trace_id>` in the URL puts that one item first (traces already answered or not in the list keep the original order).

## Reading long replies on the page

Input to the decision model stays at up to 1,500 bytes as before, and the original text a person reads on the page is saved separately in `records/text/<trace_id>.json`. The original text is up to 64 KB per field, without splitting UTF-8 characters. Both the unanswered and answered parts of the page and `shikii review query` can read this original text. The hook's quotes are still passed short, and long original text is not added as is to the model or the hook's context.

The original text is tied to the hash and the beginning of the original input, and does not rewrite decision records, truths or calibration. When the original text hits its save limit or cannot be read, the page shows it. Records from earlier versions may not have the original text kept, so fields near the save limit say so. When the original conversation has original text matching the saved beginning, it can be filled in as the original text for the page without changing the original decision.

## The AI's provisional scoring and spot checks

The scope and completion decisions at Stop do not all wait for the person's answer; the next reply from the person is tied to the same turn's decisions. UserPromptSubmit groups reflection by 2 conversations, scores provisionally from the original text and the work's outcome with `shikii_reflect` or `shikii reflect query / submit`, and marks lacking grounds as `unknown`. Notifications, other work and old Stops are handled the same as the conversation records.

Provisional scores are kept in `records/reviews/<spec>.jsonl` with the source material and grounds, and are not mixed into the person's truths. Each scoring target shows the decision model's answer and confidence first (not a truth). A score that agrees with it is kept as a machine truth (source `agreed`, never counted as the person's) and nobody is asked; a score that differs, or a held item (`unknown`), waits for the person, who sees both answers and picks one (0.11; no random sampling and no cap). The person's corrections go back to the next scorer. After a provisional score is saved, it cannot be rewritten to match the person's answer.

The page shows the person's reply, and does not highlight the AI's answer among the options. The AI's score and grounds can be read on the same page too (0.8.1 removed "simple view", and always shows everything). It also shows the counts and how often the person agreed with the AI's score. Before provisional scoring, it does not ask the person for every item, and the handling of decisions recorded in past versions is kept. There is one notice for scoring and wiki summary, and the original text is read once with query. If part of the save fails, it returns complete:false and an error per item, keeps the ones that succeeded, and lets you resend. Even in existing MCP sessions, the CLI at the absolute path the hook shows can be used.

## It does not stop on failure

No model, no answer within 5 seconds, cannot write to the store → the hook exits 0 with no output and writes one line with the reason to `~/.shikii/agent/hook.log`. The hook never stops the work. When Claude Code cannot find `shikii` (PATH), hook.log is not written either, so check with `which shikii` and Claude Code's `--debug`.

## The routine check (0.8.0): you cannot finish without the plan and the reflection

The hooks only asked "sort out the plan" and "save the reflection", so in long work these were put off and nobody noticed (in haya1, 0 needs-plan records, and evaluations of only 6 of 26 delivered lessons). Since 0.8.0 a built-in check looks at Stop: (a) if files were changed in a request where sorting out the plan was asked, and there is no `hook plan submit`, it stops once. (b) in a turn where reflection targets (conversations) were named before the request, if that conversation's provisional scores, wiki and evaluations of delivered lessons were not submitted, it stops once. The Stop after a stop goes through, but whether it was done is kept in `records/guards.jsonl` as `plan-before-work` / `reflect-before-end`, and shows in the `rituals:` line of `shikii status` (of the times asked, how many were done, and how many were done after stopping) and in "AI status" on the page. They are listed as built-in in `shikii guard list`, and there is no setting to remove them.

Since 0.11 the same built-in check also looks at the final reply (`reply-language`). The person on one machine set `language` to Japanese and still got final replies in English five times in one day. When `language` is one written in its own script (Japanese, Chinese, Korean, Russian, Ukrainian), Stop reads `last_assistant_message`, leaves out code blocks, inline code, URLs and words that look like paths or identifiers, and, if at least 60 letters remain, stops once when fewer than 20% of them are in the person's script, asking the agent to write the reply again in that language. Short replies, languages written in Latin letters and no `language` are not checked. The Stop after the block, and any later Stop of the same turn, goes through and only records whether the reply was rewritten.

## Turning a correction into a guard (0.7.3)

Lessons that could be learned by reading the repo and CLAUDE.md did not change behavior (2026-10-23, 5 tasks × 2 conditions, 4 ties), but rules the agent could not know were followed 6 of 6 times when delivered, and guards made it fix things 6 of 6 times (numbers in the guide). A correction that a machine can check becomes a "guard" in `.shikii/guards/<id>.yaml`. There are 4 kinds, `forbidden-commands` (a command about to run must match none of the patterns; refused right before it runs, 0.11), `paired-files` (if one changes, the other must too), `forbidden-words` (words not to use in added lines) and `commit-body` (words the bodies of the turn's commits must contain), and no new options. At Stop, it applies them to the difference from the list at request time (changed files), the difference from the contents at request time (added lines), and the commits since the HEAD saved at request time, and if one is hit it returns `decision: block` and the reason. At a Stop with `stop_hook_active` it does not stop, and records whether it was fixed in `records/guards.jsonl` (according to Claude Code's hooks reference, block is ignored after 8 in a row, so it stops only once). When the list or HEAD cannot be taken, it lets it through.

The agent puts a draft in place, disabled, with `shikii guard add` (JSON on standard input), and the person enables it with `shikii guard enable <id>`. enable shows that it actually stops on that kind's negative example (RED) and passes on the positive example (GREEN) before setting `enabled: true`, and does not enable it if it does not stop. `shikii guard try` shows it applied to the current working tree (commits are not checked). The counts are in the guards line of `shikii status`. The rules are in [the skill's guards.md](../skills/shikii/references/guards.md).

## How it is built

```
UserPromptSubmit ─ shikii hook user-prompt-submit ─ outcome truths for the previous request's pending (compared with the current tree)
                                                     keeps the previous reply and this message from the person as one set. Quotes conversations of similar requests in the same work
                                                     decide prompt-kind. For the new-format needs-plan, points the agent to sorting out the context with the original text
                                                     └ saves the request and the working tree's hash in sessions/<id>.json, and the working tree's list in <id>.files
SessionStart ───── shikii hook session-start ────── at the session's start and right after a summary (source compact): the rules for every request (scene always) and the last section of the newest work record under .shikii/handoff/ go into the context. Nothing to tell, nothing printed. Both agents (0.11)
PreToolUse(Agent) ─ shikii hook agent-task ──────── puts the task text and kind passed to the child in the parent's saved state (up to 10 minutes and 8 items. When adding one of the same kind, saved items of the same kind older than 30 seconds are dropped (for a child that was refused and never started). Items without a kind are treated as general-purpose. Outputs nothing. Claude Code only)
PreToolUse(Edit…) ─ shikii hook tool-lesson ─────── right before Edit / Write / MultiEdit / NotebookEdit / Bash. For Bash first a forbidden-commands guard the person
                                                     enabled: a command matching a pattern is refused (permissionDecision deny with the reason; recorded for the turn, 0.11).
                                                     Otherwise at most 1 lesson whose title, lesson or applies_to names the file (the end of its path, or its name as a whole
                                                     word) or the command (program and first word, such as git commit; options skipped) goes into the context. No model; not
                                                     before the session's first request; the same revision once an hour per session (the same record as the request's
                                                     delivery). Recorded under its own ID with the turn as parent and assessed in the reflection. Claude Code only
SubagentStart ──── shikii hook subagent-start ───── lessons close to the saved text of the same kind go into the subagent's context. With nothing saved, only the "いつも" (always) rules (the parent's saved state is left untouched except for removing the used task, and the delivery is recorded under its own ID. Claude Code only)
                                                     (limit: the child side gets no call id, so saved items are matched by kind, time and order. If you refuse the Agent tool and
                                                      start a child of the same kind again within 30 seconds, it may choose by the refused one's text)
Stop ───────────── shikii hook stop ──────────────── outcome truths for the remaining pending (if changed, settled as edit; if not, carried over with !edit)
                                                     compares the list at request time with the current one for "changed files" → decide changes-in-scope, done-as-asked (in parallel, once per request)
                                                     └ saves last_assistant_message (matched with the person's next message, and needs-plan's context). One line summarizing what waits for an answer. Draws the line if the 4 specs' truths reach min_n
```

- It does not read the transcript (its shape is not documented). Per-session saved state is `.shikii/sessions/<session_id>.json` (request, previous, pending, asked, judged; removed after 7 days) and `<session_id>.files` (the `git ls-files --stage` list at request time; up to 4 MB). Claude Code runs hooks in parallel (Stop and the next request overlap), so the saved state is read → changed → written (written to tmp and renamed) inside a flock. The lock is held briefly (model calls are outside the lock), and if it cannot be taken after waiting 2 seconds, it goes on without the lock
- The working tree's state is taken at the repo root (even for a session started from a subdirectory it looks at the whole repo): `git add -A` into a temporary index (.gitignore is respected; untracked files are included but `.shikii/` is excluded), the id (hash) of the tree from `git write-tree`, and that index's list (the blob id per file). HEAD and the index are not included, so commit / stash / checkout alone do not change it; it changes only when file contents change. New blobs are written to temporary objects and removed, so the contents of untracked files (`.env` and so on) do not stay in the repo's `.git/objects` (the list has no contents either, only paths and ids). If the whole takes more than 3 seconds (a huge node_modules with no .gitignore and so on), no truth is set, and the changed files are treated as unknown. The list (mode and blob id per file; changes of chmod alone are counted too) is read up to 4 MB and then stops. Outside git there is no prompt-kind truth and no changes-in-scope, and done-as-asked's files is `(unknown: no git listing for this turn)`. Limits: changes by another agent or formatter running at the same time are also counted as "changed". `git add` runs the repo's clean filters (Git LFS and so on) as usual (the same side effects as an ordinary `git add`; worth knowing in repos that have filters)
- The list of changed files in the question is at most 30 (the rest is `... and N more`). If nothing changed, changes-in-scope is not asked, and done-as-asked's files is `(none)`
- A bare acknowledgement (a fixed list such as "ok", "yes", "go ahead" and their Japanese equivalents; since 0.9.3 a short request with content, such as "merge main", is a request of its own) does not replace the request but is attached to the previous one (so the end-of-turn questions do not read "ok" as the request). Even a short reply is a new turn, so judged is reset and the turn after "ok" is evaluated again (the request text is "previous request / ok", a separate input)
- That list is only the hook's provisional decision. When the agent is asked for the pre-start organizing, `continues_previous` in `hook plan submit` decides (since 0.9.3): `true` attaches the message to the previous request ("go on", "OK, let's do that", a thumbs-up), `false` makes it a request of its own ("merge main"), and leaving it out keeps the list's decision. It corrects only the same session and turn, and only until that turn's Stop has judged the request. The previous request's done-as-asked outcome is settled from this message by fixed rules whatever the grouping (a restatement: not done; a different message of 40 characters or more: done, partial weight; an acknowledgement or a short message: nothing), so the grouping can neither erase nor make a truth. The organizing is the agent's hypothesis and only decides the grouping, never a truth. When a session is closed or killed mid-turn (no organizing, Stop or next request comes), the waiting outcome is settled once with the provisional grouping by the next hook of the project or a reflect query, after 30 minutes or as soon as the session record shows the turn moved on
- Claude Code skips the organizing in turns that change no files. When the person's message is short (under 40 characters), not in the acknowledgement list, and nothing was submitted for the turn, the Stop stops once (even with no file changed) and asks only for `continues_previous`, giving the minimal `hook plan submit` JSON (agreed and open as `unknown:true`). That Stop does not judge the turn and leaves the grouping open; the Stop after the block (`stop_hook_active`) judges it, without stopping again, with the grouping the agent gave, or the list's when none came If that Stop never comes (the person pressed Esc, the session was closed), the person's next request judges the turn with the reply its first Stop kept, without rechecking the person's checks or the rituals; a turn the person's check stopped is judged the same way (0.9.3)
- `restates` in `hook plan submit` names the earlier request of this session that the message restates (the turn id of any earlier request of this session, however far back: the `<id>` of `history:<id>:user` in query, or one the agent saw earlier; since 0.9.3). shikii looks the request up in its own record of this session and project; query still shows only the recent turns. The message is compared with that request's own text by the same fixed rule: similarity 0.6 or more gives that request's done-as-asked "no" (weight 1) and the previous request then gets nothing from this message; otherwise nothing. A turn of another session or project, an unknown turn, or a request that already has a truth is ignored, and the usual comparison with the previous request applies
- Completion notifications of background work (`<task-notification>` / `[SYSTEM NOTIFICATION - NOT USER INPUT]`, which Claude Code sends as a "user message" when a subagent or background command ends) are not requests: the 2 questions before thinking are not asked, and the request, list and pending are not replaced (measured: nearly half of the records were these). If work continues after a notification, at the end of that turn it judges "in scope / finished" again against the original request (the owner's choice: measure the final state of long background work; one request gets as many decisions as notifications)
- Overlap: even if the next request B writes saved state while Stop (request A) is waiting for the model, Stop A's marks (judged, previous, the saved reply) only hit A's saved state (it also compares a per-request identifier, so requests that repeat the same text are distinguished). pending settles only the traces it saw, and the list is compared only when the hash of the request on the first line matches. UserPromptSubmit with an `agent_id` (subagents and so on) is not a person's request, so it does not change the saved state
- A hook.log line is cut at 400 bytes (the model's error text sometimes comes with the response body)
- The contract on the Claude Code side (the official hooks reference, 2026-10-18): a hook receives `session_id` `cwd` `prompt` `stop_hook_active` `last_assistant_message` on stdin, and can return `hookSpecificOutput.additionalContext` (UserPromptSubmit) and a top-level `systemMessage` on stdout. Returning `hookSpecificOutput` at Stop continues the conversation, so it does not return it
- The contract on the Codex side (learn.chatgpt.com/docs/hooks, 2026-10-19): the same event names and stdin keys (`Stop` also has `last_assistant_message` and `stop_hook_active`), plus Codex-only `turn_id` and `model`. Stop's output is JSON or nothing (shikii outputs JSON when it outputs, and nothing otherwise). Codex 0.164 reads the same `{"decision":"block","reason":…}` as Claude Code, takes the reason as a message on the person's side and continues the same turn (the second Stop has `stop_hook_active`; checked in the 0.9.2 audit). shikii does not tell Codex and Claude Code apart (both get the same 2 questions)

## For people moving from claude-jev

1. First remove jev with `uninstall.mjs` where you put claude-jev (e.g. `node ~/dotfiles/claude-jev/uninstall.mjs --yes`) (with both installed, the same event is judged twice)
2. Node is not needed. The store moves from `~/.claude/jev/` → `~/.shikii/agent/`. Old records (`~/.claude/jev/decisions-store`) are not carried over (the spec wording differs, so they are no material for lines)
3. There are no fixed thresholds (go ahead at 0.75, check at 0.60). It does nothing until a line is drawn, and acts by band once one is
4. prompt-intent → prompt-kind (the same 5 options). There is no command classification (jev's PreToolUse): only the forecast of the request and the self-evaluation at the end are measured. There is no model routing (jev-router) either

For people moving from the hooks of shikii's earlier version (2026-10-18): running `shikii hook install --yes` again removes shikii's PreToolUse hook from settings, and copies the 2 new specs. `~/.shikii/agent/decisions/command-effect.yaml` and `edit-in-scope.yaml` and their records are not deleted (delete them by hand or move them elsewhere if you do not need them).

## Adding it to other agents

Only 3 things are needed:

1. Where you want a decision, call `shikii decide <spec> --json -i key=value` and receive `band` and `trace_id`
2. Where the outcome is known (at the end, on cancel, when the user chooses), call `shikii label <trace_id> <truth> --source outcome`. If you only know "it was not that", use `!option`; if weak, `--weight 0.7`
3. For context that must not be sent (personal information, production data), add `--tainted`. If the spec's `send_to` has no `local`, it becomes abstain

## When to use the skill (rules), MCP (entry point) and hooks

- **hooks** (this document): record the AI's own thinking right after the request and at the end of the turn. The new-format pre-work decision is called by the usual agent after sorting out the context with the original text
- **MCP** (`shikii mcp`, [mcp.md](mcp.md)): the entry point for business decisions, called by an agent or a program itself when "this decision is needed now"
- **skill** (`skills/shikii/SKILL.md`): the rules for working with shikii. When to call a decision, how to follow bands, that truths, lines and state belong to people, that tune adoption comes after the person's "the meaning is the same", and decisions whose text must not leave the machine. CI checks the front matter and that references exist with `scripts/check-skill.sh`
