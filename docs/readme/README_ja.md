# shikii: エージェントを、あなたのプロジェクトに合わせて育てる

AIエージェントは、メモリーで以前の仕事を引き継げます。プロジェクトでは、その経験を必要な時に使い、役立ったかを確かめ、判断をどこまで任せるかも測っていきたい。shikiiは、この流れをつなぎます。言われたこと・決めたこと・確かめたことを `.shikii/` に貯め、関係する知識を届け、結果を次の仕事へ戻します。育つのはモデルではなくプロジェクトの側なので、モデルを替えても知識は残ります。

**言ったことを覚え、二度言わせず、任せられる範囲が広がる。**

## 困りごと

エージェントに仕事を頼むと、こうなりがちです。

- 一度直してもらったことを、次の仕事でまた直している
- 教訓を書き残しても、エージェントが読んだのか、読んで行動が変わったのかが分からない
- サブエージェントに任せた仕事には、その教訓がそもそも届かない
- 決まっていることを確かめずに作業を始め、学んだことを書き残し忘れる
- 報告・メモ・画像がrepoに散らばるか、セッションが終わると消える
- AIの「たぶん、0.9」をどこまで信じて任せてよいのか、誰も測っていない

人が毎回同じ説明と訂正を繰り返すなら、AIに任せた意味がほとんどありません。

## 何が育つか

そのプロジェクトで長く働いた人のように、エージェントが次の5つを身につけます。育つのはモデルではなく、プロジェクトの `.shikii/` の側です。

<p align="center"><img src="../assets/shikii-grows-ja.svg" alt="育つもの5つが閾を越えて、それぞれの置き場(wiki/・guards/・整理と振り返り・handoff/・ask → act)へ入る" width="60%"></p>

| 育つもの | shikiiがすること |
|---|---|
| 言われたことを覚えている | 訂正や決めたことが出典付きの教訓になり、似た仕事の前に届く |
| 同じことを二度言わせない | 機械で確かめられる訂正は、ターンの終わりに確かめ、コマンドは流す直前に断る「止める検査」になる |
| 決まった手順を踏む | 依頼の前に要る知識をそろえて渡し、終える前に結果と学んだことを保存させる。抜けると止まる |
| 仕事の跡を残す | 報告・リリースの記録・差分・画像を作業記録に残し、画面で読める |
| 任せてよい範囲が広がる | 正解が貯まるほど「ここより上なら当たる」線が引け、人に聞かずに進める判断が増える |

1. **言われたことを覚えます。** 普段の会話の依頼・返答・訂正から、エージェントが出典付きの教訓をwikiに書きます。教訓には種類(このプロジェクトで決められたルール・やり方・判断の基準・前提と事実・経緯)と、その仕事の言葉で書いた場面(「コミットする時」「請求書を出す時」など)が付きます。保存の前に、決定モデルが差し込み先の記事を探し、前の教訓と食い違わないかを見ます。1つの話題は1つの記事にまとめます。似た依頼の前には関係する教訓が最大2件届きます。Claude CodeとCodexでは、教訓に名前が出てくるファイルを変える直前や、コマンドを流す直前にも届きます。サブエージェントには、始まる時にいつもの決まりが届き、Claude CodeとCodexではコマンドやファイルの直前にその名前が出てくる教訓も届きます。経緯の教訓は、探した時にだけ読みます。エージェントが自分で作った・変えた決まりやテストや手順も、頼まれなくてもその場でwikiに書きます。
2. **同じことを二度言わせません。** 「変更履歴は英語と日本語を揃える」「この語は使わない」「コミット本文に元の問題と検証を書く」のように機械で確かめられる訂正は、止める検査になります。引っかかるとエージェントは終われず、直してから終えます。「許すまで push しない」のようなコマンドの検査は、Claude CodeとCodexではコマンドを流す直前に断ります。
3. **決まった手順を踏みます。** 依頼が来ると、hookが今回の依頼、それまでの会話で決まったことと未決のこと、関係する教訓、見直しを待つ記事をそろえてエージェントに渡します。エージェントはそれを読んでから作業し、話題が移ったら自分で選んだ語でwikiを探し直します。終える前に、結果と、届いた教訓が役立ったかと、学んだことを1回で保存します。保存が無いまま終えようとすると、shikiiは打つべき操作をエージェントへ返します。残りが減れば続きを促し、減らなければ未完了と表示して自動の続きを止めます。この確かめは組み込みでいつも効き、`CLAUDE.md` や `AGENTS.md` の無いプロジェクトでも効きます。
4. **仕事の跡を残します。** 書き換えながら進める監査の報告・リリースの手順・差分・画像は `.shikii/handoff/<仕事>/` に入り、サブエージェントにも報告をここへ書くよう伝えます。repoにはコミットされず、人は画面の「知識 → 作業記録」で読みます。
5. **任せてよい範囲が広がります。** モデルは「たぶん0.9」と確率を返します。shikiiは人と結果が付けた正解から、モデルの自信と当たる割合の関係を測り、「ここより上なら自動で進めてよい」という線を引きます。線が引けるまでは自動では動きません。判断はすべて4つに分かれます。`act` は自動で進める、`ask` は人に確かめる、`discard` は動かない、`abstain` は入力か接続先が足りない、です。線が引けた時と、正解が足りても線を引けない時(答えが片方だけ、答えを見分けられない、またはそのために問いを止めた)は、ターンの終わりに一度だけ知らせます。正解はモデルと別に残るので、モデルを替えても最初からやり直しません。別の聞き方を同じ正解で採点し、良い方を残すこともできます。意味が同じかはエージェントが確かめ(英語以外の設定ならその言語に両方を訳し)、同じならその聞き方に変えて知らせます。違っていたら元に戻せます。エージェントが決めきれない時だけ人に聞きます。

効いているかは、画面の「AI の様子」と `shikii status` で見ます。届けた教訓が役立ったか、手順を踏んだターンの数、止める検査が止めて直った数、人を待つ判定の数、引けた線が出ます。

## 人がすること

- **普段どおりエージェントを訂正する。** 会話の中で「まだ英語が残っている」と言えば十分です。エージェントが教訓にし、shikiiが正しい記事の隣に置きます。機械で確かめられる訂正なら、エージェントが止める検査の草稿（無効）も置きます。
- **止める検査を有効にする。** `shikii guard enable <id>` を一度打ちます。shikiiは、その検査がわざと壊した例で実際に止まり、正しい例で通ることを見せてから有効にします。外すのも人の判断です。
- **いくつかの答えを付ける。** 画面の「答える」に、モデルが迷った判断と、自動で進めた判断の20件に1件が、1枚ずつ出ます。待っている数は「答える」の横に出ます。会話を読んで、本当はどうだったかのボタンを押します。
- **知りたい時に知識を引く。** 画面の「知識」の一番上の「いつも守ること」に、人やAIが決めたこのプロジェクトのルールが並び、埋もれません。新しいルールには「新」のラベルが付きます。その下で場面を選ぶと、その場面に効く教訓が種類ごとに並び、題を押すと本文が出ます。全部を確かめる必要はありません。「あなたに見てほしいもの」に、害があった教訓や繰り返された訂正のような例外だけが出ます。
- **知識を編集・削除する。** 記事を開いて「編集」「削除」を選べます。削除すると検索や配信から外れ、出典と履歴は残ります。AIが役に立たないと判断したあなたの過去の答えは「AI が無効と判断した過去の答え」に並び、そこから元に戻せます。
- **読みたい時に作業記録を読む。** 画面の「知識 → 作業記録」で、エージェントの報告を読み、画像を見られます。
- **聞き方が変わった時に確かめる。** エージェントが問いの聞き方を変えると、「答える」に知らせが出ます。「このままでよい」か「元に戻す」を選びます。エージェントが意味が同じか決めきれなかった時も、ここで選びます。
- **整理したい時に頼む。** 「shikiiを整理して」と頼むと、エージェントがwikiの文章を出典と照らし、言い過ぎや同じ説明の繰り返しを直します。意味・条件・例外・履歴は保ちます。
- **記憶を最適化したい時に頼む。** 「shikiiを最適化して」(記憶の最適化)と頼むと、エージェントはその回のうちに、記憶の更新を待つwikiの記事を全部、まず整理し、続けて今の版の書き方に合わせて原資料と照らして見直します(記憶の更新)。原資料が読めずに見直せない記事は、理由を残して飛ばします。整理だけなら「shikiiを整理して」、更新だけなら「記憶を更新して」と頼みます。

それ以外は機械の仕事です。

## 始め方

### 1. TypeSafeのAPIキーを置く（推奨）

[TypeSafe AI](https://docs.typesafe.ai/introduction/quickstart)でAPIキーを取得し、シェルとエージェントの環境変数に置きます（`export TYPESAFE_API_KEY=…`）。取得するものはなく、普通のPCで動きます。APIキーがあれば、hookも既製の問いもJevへ送り、手元のモデルは起こしません（`shikii up` も起こしません）。既製の問いのために、依頼文・エージェントの返答・wikiの教訓がTypeSafeへ送られます（手元の記録にも残ります）。APIキーを置いたまま手元のモデルを使うなら `SHIKII_MODEL=local`、Jevに固定するなら `SHIKII_MODEL=hosted` を置きます。

**APIキーを置けない時はllama.cppです。** APIキーが無ければ手元のモデルを動かします。27Bのモデルなので動作中のメモリが約10GB要り、普通のPCでは重いことがあります。macOSでHomebrewなら:

```sh
brew install llama.cpp
llama-server --version
```

macOS以外は[llama.cppの公式の手順](https://github.com/ggml-org/llama.cpp/blob/master/docs/install.md)を参照してください。手元の基本モデルは **Ternary-Bonsai-27B Q2_g64**（`prism-ml/Ternary-Bonsai-27B-gguf`、Apache 2.0。取得は約7.6GB、動作中のメモリは約10GB）です。`shikii up` がllama-serverを `:8086` に、`shikii-readout` を `:8080` に立てるので、hook・MCP・画面は常に `:8080` を見ます。他のGGUFも同じ形で使えます（`shikii up --gguf <file>`）。

### 2. shikiiをインストールする

```sh
curl -fsSL https://raw.githubusercontent.com/hayaenfj/shikii/main/install.sh | sh
```

インストーラーは、GitHub Releasesからこの機械向け（macOSかLinux、amd64かarm64）の最新版を取ってきて、版の `SHA256SUMS` と照らしてから、`shikii` と `shikii-readout` を `~/.local/bin` に置きます。どれが最新版かをGitHubに聞くので、出したばかりの版もすぐ入り、Goは要りません。実行ファイル、hook（依頼の前・作業の後・サブエージェントの始まりと終わり・ファイルの変更とコマンドの直前）、エージェントの作法を入れ、PATHに足す必要があれば案内します。Codexでは `/hooks` でhookを信頼してください。hookの中身が変わるたび(実行ファイルを動かした時やshikiiを更新した時)にもう一度信頼が要り、それまでCodexはhookを飛ばします。

**Go 1.27以上がある場合。** 両方の実行ファイルを、Goの版を上げても残るフォルダへ直接入れられます。

```sh
mkdir -p "$HOME/.local/bin"
GOBIN="$HOME/.local/bin" go install github.com/hayaenfj/shikii/cmd/shikii@latest
GOBIN="$HOME/.local/bin" go install github.com/hayaenfj/shikii/cmd/shikii-readout@latest
export PATH="$HOME/.local/bin:$PATH"
shikii hook install --yes
```

シェルの設定でも `~/.local/bin` をPATHに加え、続けて手順3で利用するプロジェクトを初期化してください。版を指定する時は、両方のコマンドの `@latest` を `@v0.34.0` のようなタグへ置き換えます。

Goを上げた後や実行ファイルを動かした後にhookが働かなくなったら、上のインストーラーのコマンドをもう一度流してください。多くは実行ファイルそのものが消えていて(miseのようなGoの版の管理ツールでは、Goを上げると `go install` が置いた版ごとのフォルダごと消えます)、`shikii doctor` も一緒に消えています。`shikii` がまだ動く時は `shikii doctor` を流すと、hookやCodexの登録が、もう無い・動かせないshikiiの実行ファイルを指している時はそう言い、直し方を出します。

**前に `go install` でGoの既定フォルダへ入れた人へ。** その実行ファイルはGoのフォルダ(`$(go env GOPATH)/bin` か `GOBIN`)に残り、`shikii update` もそこで更新するだけで、`~/.local/bin` へは移しません。上のインストーラーのコマンドを一度流すと、hookは `~/.local/bin/shikii` を動かすようになります。先に `~/.local/bin` がPATHにあることを確かめてください(無ければインストーラーがそう言います)。Claude CodeとOpenCodeのMCPは `shikii` を名前で動かします。そのあとGoのフォルダの古い `shikii` と `shikii-readout` を手で消し、もう一度 `shikii hook install --yes` を流してください。それまでは実行ファイルが2つあり、端末で打つ `shikii` と、Claude CodeとOpenCodeのMCP(`shikii` を名前で動かす)は、PATHで先に見つかる方を動かし(`command -v shikii` でどちらかわかります)、`shikii update` はその1つだけを更新し、CodexのMCPの登録は古い実行ファイルが残る間はそちらを指したままです。

**ソースから組む（開発する人向け）。** このリポジトリをcloneした中で `sh install.sh` を流すと、今のソースをGo 1.27以上で組んで同じ `~/.local/bin` に置き、hookも同じように入れます（`make install` は組んで実行ファイルを写すだけです）。

### 3. 利用するプロジェクトを初期化する

使いたいプロジェクトで、エージェントにこう頼みます。

> このプロジェクトでshikiiを使って

エージェントが `shikii init` を実行します(`shikii --init` と同じで、自分で実行しても同じです)。shikiiは、初期化したプロジェクトだけで動きます。

`shikii init` がすること:

- プロジェクトに `.shikii/` を作り、既製の問い・wiki・止める検査の置き場・作業記録の置き場を用意します。`.shikii/` には私的な会話が入るので、Gitの除外に入れます。
- エージェントがshikiiを呼べるように、MCPの設定を足します。プロジェクトに `.mcp.json` と `opencode.json` を足し、`AGENTS.md` と `CLAUDE.md` には書きません。MCPを共通の `~/.codex/config.toml` からしか読まないCodexには、プロジェクトを書かない共通の登録を1つ書き、道具を呼ぶたびにエージェントの作業フォルダを `project` で渡します。この登録には `default_tools_approval_mode = "approve"` を書くので、Codexはshikiiの道具を、呼ぶたびに確認せずに実行します。確認してほしい時は、そこを `"prompt"` と書くか、行を消します。shikiiが足し直すことはありません。
- エージェントの作法(skill)を置きます。
- この機械で最初のプロジェクトで、shikiiのhookが1つも入っていない時は、hookも入れます(`shikii hook install --yes` と同じ。TypeSafeのAPIキーが無く `llama-server` が入っている機械では、手元のモデルを裏で起動します)。すでにプロジェクトがあってhookが無い機械では、hookは入れずに、入れるコマンドを表示します。
- 何度実行しても同じ結果になり、あなたが書いた設定や記録は消しません。

`shikii init` には選ぶものが無いので、`--yes` のような引数は受け付けません(付けると、引数は要らないと断ります)。`--yes` を付けるのは、変える前に一覧を見せるコマンドです。

| コマンド | `--yes` 無し | `--yes` 付き |
|---|---|---|
| `shikii hook install` | 足すhook・プラグインの一覧を出すだけ | 入れる |
| `shikii uninstall` | 外す物の一覧を出すだけ | 外す |

答え合わせの画面はプロジェクトごとに1つで、最初の依頼のhookが空いているポートで起こしてブラウザで開きます(URLは `shikii page`)。`shikii doctor` で状態を確かめます。

**OpenCodeについて。** OpenCode 2.xにはhookの設定ファイルが無いので、`shikii hook install --yes`(と、この機械で最初の `shikii --init`)が、小さなプラグインを `~/.config/opencode/plugins/shikii/` に置きます(`$XDG_CONFIG_HOME` が絶対パスの時は、その下の `opencode/` です)。Claude CodeやCodexと同じhookを動かすので、依頼の前にshikiiの教訓がモデルに届き、必要な記録が残っていなければ、回の終わりに続きを促します。この終了時の確認は、OpenCode の試験段階の hook(OpenCode 2.3.0)を使って回の中で動くので、TUI でも `opencode run` でも動きます。その hook を動かさない OpenCode では回が終わった後にしか確認できず、自前のサーバーで動く `opencode run`(`--standalone`、または常駐のサービスが動いていない時)はその時にはもう終わっています。同じ名前のあなたのフォルダは上書きせず、リンクもたどらず、その旨を表示して残します。`OPENCODE_CONFIG_DIR` を設定して起こしたOpenCodeは、そのフォルダの `plugins/` からだけプラグインを読むので、shikiiのプラグインを読みません。shikiiはそこへは書かず、`shikii doctor` がそう知らせます。OpenCode 1.xはこのフォルダを読まず、これまでどおりMCPの設定とskillだけを使います。shikiiのプラグインはコマンドの前のhookを持たないので、コマンドを拒む止める検査はOpenCodeでは動きません(終了時の確認は動きます)。shikiiのプラグインはあなたへ文も見せないので、Claude CodeやCodexで表示するshikiiの文(止める検査の説明、答えを待つ数、自動の続きを止めた知らせ)は、OpenCodeには出ません。入れた後はOpenCodeを開き直してください。

**`OPENCODE_CONFIG_DIR` を使うOpenCodeについて。** それを設定して起こしたOpenCodeにshikiiのプラグインを読ませるには、そのフォルダの `plugins/` へ、shikiiのフォルダのリンクを自分で置きます: `mkdir -p "$OPENCODE_CONFIG_DIR/plugins" && ln -s ~/.config/opencode/plugins/shikii "$OPENCODE_CONFIG_DIR/plugins/shikii"`(`shikii doctor` があなたのパスでこのコマンドを出します)。リンクはあなたの物なので、`shikii uninstall` は残します。外した後は自分で消してください。

### 4. 前のメモリをshikiiに移す(任意)

Claude CodeやCodexのメモリーに、このプロジェクトのことがすでに書いてあるなら、エージェントにこう頼みます。

> メモリをshikiiのwikiへ移して

一度頼めば十分で、ファイルを先に仕分ける必要はありません。エージェントは次のように移します。

- 読むのは、Claude Codeのメモリー(`~/.claude/projects/<プロジェクト>/memory/`)と、Codexのメモリー(`~/.codex/memories/`)のうちこのプロジェクトに関わるファイルです。ほかのプロジェクトのファイルには触りません。秘密と、会話の記録そのものは移さずに残します。
- 各ファイルの本文を、そのままwikiの原資料として控えます。
- そこから出典付きの教訓を作り、同じ話題の記事がすでにあれば、その記事にまとめます。使わない語のように機械で確かめられる決まりは、止める検査の草稿(無効)も置きます。
- 元のメモリーのファイルは消さず、本文も変えません。各ファイルに、移した先のwikiの記事を示す1行だけを足します。どの依頼にも効く決まり(言葉の決まりなど)は、元の索引にも残します。

まだ移していないファイルがあると、hookがセッションに1回、その数とファイル名を知らせます。

### 更新

```sh
shikii update
```

`shikii update` は最新の安定版を取得し、ハッシュを確かめ、shikiiとreadoutを置き換えます。置き換えたshikiiを、shikiiのhookかOpenCodeのプラグインのどれか1つが動かしていれば、updateは続けて `shikii hook install --yes` を自分で実行し、3つのエージェント全部(Claude Code・Codex・OpenCode)のshikiiのhookを書き直します。手で外したhookも戻ります。新しい版がエージェントの設定に加える変更も、表示しながら反映します。この段で失敗した時はupdateがそう言うので、`shikii hook install --yes` を実行してください。0.31.0からは、shikiiが書いたCodexの登録に `default_tools_approval_mode = "approve"` を足し、Codexがshikiiの道具を、呼ぶたびに確認せずに実行するようになります。hookを使わない場合は、代わりに初期化済みのプロジェクトで `shikii --init` を実行し直します。同じ行が足され、hookは無効のままです。**0.6.0以前からの更新は、初期化済みの各プロジェクトの `.shikii/` の中を全部消して初期化し直します。** 以前の会話・教訓・正解・較正は消えます。残したいものは先に控えてください。0.7.0以降からの更新では残ります。更新後は画面とMCPを再起動してください。

同じプロジェクトへ書く機械やプロセスがほかにもあれば、全部を同じ版にしてください。更新の後はエージェントのセッションも開き直します。既存の記録は残ります。新しい版で記事の書き方の方針が変わった時は、原資料を残したまま既存の記事を見直す作業(記憶の更新)が、作業の区切りに少しずつエージェントへ届きます。進捗は英語で表示します。詳しくは[記憶と学習](../memory-and-learning.ja.md)を参照してください。

0.8系からの更新では、開いているエージェントのセッションも開き直し、同じwikiを使う機械を全部0.9.0以上にします。0.8系のshikiiは種類と場面を付けた記事を読めず、wikiへの保存を断ります(記事は壊れません)。同じように、0.9.1以前は0.9.2が書いた記事(記事のファイルの決まった語が英語)を「変更あり」と見なすので、同じwikiを使う機械は全部0.9.2以上にします。

0.28.0へ更新した後は、同じwiki・進行中のセッション・担当割り当ての記録を書く全プロセスを更新し、セッション・画面・MCPを再起動してください。旧版は新しい読取計測・品質報告の進捗を保持できません。hookなしの場合は既存の初期化済みプロジェクトで`shikii --init`を再実行すると、データを保持しhookを有効にせずskillを更新できます。0.27.0からの更新ではデータと既存の記事・実行結果を保持します。条件に合う結果の選択には0.25.0以降が必要です。chitenから実利用・実行結果を返す場合は、対応するchitenも別途必要です。0.24より前の書き手は担当のcontextやイベントとreceiptの対応を保持できず、0.22より前の本体では学び付きの記事を読めません。旧版へ戻す必要がある場合は、更新前の`.shikii/`を控え、本体とデータを一緒に戻せるようにしてください。

0.9.6からの更新では、この機械に登録された全プロジェクトに、置き場のidを1回だけ書きます。更新の後に移したプロジェクトのフォルダは、自分でつなぎ直ります(更新の前に移した物はつなぎ直りません。hookがそう知らせ、そこで `shikii --init` すればwikiと記録はそのまま使えます)。機械を全部上げ、エージェントのセッションを開き直してください。古いshikiiがプロジェクトをもう一度登録すると、hookがそう知らせ、全部のshikiiを上げるよう頼みます。

0.9.2以前からの更新では、古いshikiiが書いたCodexの登録をそのまま残します(0.9.7から書き直しません)。initと更新が、代わりに書く節を出します。`args = ["mcp", "--local", "http://127.0.0.1:8080"]`(全部のプロジェクトで1つの登録)の形です。直した後はCodexを開き直してください。直すまでは、`--store` で1つのプロジェクトを指す節のままなら、どのCodexのセッションもその1つのプロジェクトを使います。古いshikiiが `AGENTS.md` に足した節も残し、initと更新が手で消す範囲を知らせます。

### アンインストール

```sh
shikii uninstall        # 外す物の一覧を出すだけで、何も変えない
shikii uninstall --yes  # 外す
```

shikiiがエージェントに入れた物を外します。`~/.claude/settings.json` と `~/.codex/hooks.json` のshikiiのhook、OpenCodeのプラグインのフォルダ `~/.config/opencode/plugins/shikii`(shikiiが置いた物だけ。ほかのプラグインは残ります)、`~/.codex/config.toml` の `[mcp_servers.shikii]`、初期化した各プロジェクトの `.mcp.json` と `opencode.json` のshikiiの項目、`~/.claude/skills/shikii` と `~/.agents/skills/shikii` のエージェントの作法です。プロジェクトの答え合わせの画面も止めます。ほかのhook・MCP・設定、ファイルそのもの、`AGENTS.md` と `CLAUDE.md` は残ります。データも残ります。各プロジェクトの `.shikii/` と `~/.shikii/agent` は消さず(止めた画面の記録だけは消します)、もう一度インストールすればその続きから使えます。実行ファイルは消しません。最後に、そのパスを入れた `rm` のコマンドを出します。外した後は、開いているClaude Code・Codex・OpenCodeのセッションを開き直してください。

## 仕組み

<p align="center"><img src="../assets/shikii-conversation-ja.svg" alt="毎回のターンで、作業の前に読み、作業中は跡を残し、終える前に振り返る。教訓は次の依頼で届く" width="100%"></p>

### 1回の依頼の流れ

hookを入れると、shikiiは人の依頼1つと、それに対するエージェントの作業と返事を1回として、次の時に動きます。

1. **依頼の前。** 依頼を控え、今回の依頼、それまでの会話、関係する教訓、見直しを待つ記事をそろえてエージェントに渡します。前の依頼の続きだけの発言(「ok」「続けて」「それでいこう」など)は前の依頼にまとめます。続きかどうかはエージェントが決め、決まった相づちの一覧は予備です。決定モデルには「始める前に進め方を合わせるべきか」を聞きます。セッションの始めには、どの依頼にも効く決まりと、進んでいる作業の様子を渡します。
2. **作業の途中。** Claude CodeとCodexでは、ファイルを変える直前とコマンドを流す直前に、その名前が出てくる教訓を渡し(エージェントは、その呼び出しの結果と一緒に読みます)、有効にしたコマンドの止める検査はその場で断ります。サブエージェントには、起こす時にいつもの決まりを渡し、仕事に要る物はサブエージェントが自分でwikiを探します。エージェントは、話題が移った時や迷った時に、wikiを探し直したり、決定モデルに聞いたりできます。
3. **終える時。** 結果の保存、届いた教訓の振り返り、記事の分類、返事の言語がそろっているかを確かめ、止める検査をそのターンで変わったファイル・足した行・コミットに当てます。足りない物があれば、具体的な操作をエージェントへ返します。そろってから、決定モデルに「変更は範囲内か」「頼まれたことを終えたか」を聞いて記録します。
4. **次の依頼の時。** 前の答えに、その後に起きたことから正解が付きます。次の依頼までに戻された変更、言い直された依頼、まとめられた・置き換えられた教訓、振り返りで役に立った・使われなかったと評価された教訓です。結果で答えが決まらない問いだけが、人の答えを待ち、その数は画面に出ます。

### 決定モデルに聞くこと

決定モデルは、文章を書かずに、はい/いいえや選択肢の確率だけを返すモデルです。推奨はTypeSafeのJevで、APIキーを置けない時は手元のTernary-Bonsai-27Bを使います。shikiiは、エージェント自身の仕事についての次の問いを初めから持っています。

| 問い | 聞く時 |
|---|---|
| 始める前に、進め方を人と合わせるべきか(`needs-plan`) | 依頼の前 |
| 届けようとする教訓は、今の仕事に当てはまるか(`lesson-applies`) | 教訓を届ける前 |
| 新しい教訓はどの記事に入れるか、前の教訓と食い違わないか | 教訓を保存する前 |
| 変えたファイルは、頼まれた範囲に収まっているか(`changes-in-scope`) | 終える時 |
| 頼まれたことを終えたか(`done-as-asked`) | 終える時 |

これらの答えが助言として届くのは、線が引けてからです。どの答えも、エージェントの道具の実行を止めることはありません。

### 止める検査

止める検査は決定モデルではなく、決まった規則です。ターンの終わりに、そのターンで変わったファイル・足した行・コミットに当てます。流してはいけないコマンドの検査は、Claude CodeとCodexではコマンドを流す直前にも断ります。種類は4つです。

| 種類 | 止める時 | 例 |
|---|---|---|
| `paired-files` | 片方のファイルが変わったのに、もう片方が変わっていない | `CHANGELOG.md` と `CHANGELOG_ja.md` |
| `forbidden-words` | 足した行に使わないと決めた語がある | 言い換えを決めた語。例外のパスは見ない |
| `commit-body` | そのターンのコミットの本文に決めた語が無い | 「元の問題」「変更後」「検証」 |
| `forbidden-commands` | 実行前のコマンドが規則に合う | 公開を許可するまで `git push` を断る |

エージェントは訂正から草稿を置き（`shikii guard add`、無効）、人が `shikii guard enable <id>` で有効にします。有効にする時、shikiiはその検査がわざと壊した例で止まることと、正しい例で通ることを先に見せます。引っかかったターンはエージェントが終われず、直してから終えます。同じ検査が同じターンを止めるのは1回だけで、その検査が止めた後の続きでは止めず、直ったかだけを記録します。

### 知識の手入れ

教訓は書いて終わりではなく、使われ方を見て直していきます。

- **役に立たない教訓は届けない。** 同じ場面で繰り返し使われなかった教訓や、判断を妨げた教訓は、判断と証拠を付けて見直しに回ります。エージェントが出典を確かめてから直し、変えなくてよいという判断も残せます。分からない評価は、悪い評価として数えません。判断を妨げたという評価は、付いた版にだけ数えます。
- **あなたの過去の答えも同じ。** 似た依頼の前に示すあなたの過去の答えも、示しても役に立たなければ示さなくなり、画面の「AI が無効と判断した過去の答え」に並びます。画面から元に戻せます。
- **経験を手順に育てる。** 前に使った手順は、その時の条件・失敗・直し方と一緒に読み、今回の条件と比べます。前の成功を、そのまま今回の成功とは見なしません。
- **エージェントの間で分け合う。** 同じプロジェクトにつないだClaude Code・Codex・OpenCodeは、同じwikiを使います。ひとりの発見をほかの担当に届け、別の条件で確かめて、同じ知識に戻します。
- **読む量と進め方も結果から選ぶ。** どれだけ読めば足りるかや調査の進め方を、実際の結果から選び直します。別の2つの仕事で確かめてから採用し、悪くなったら前のやり方に戻します。
- **版が上がった時の見直し。** 記事の書き方の方針が変わると、作業の区切りに既存の記事を少しずつ、原資料と照らして見直します。

別に使う道具のchitenと組むと、chitenが報告した知識の実際の使用と手順の結果も、同じ記録に入ります(任意)。詳しくは[メモリーとの違い](../memory-and-learning.ja.md)と[ガイド](../guide.ja.md)にあります。

### 誰が何をするか

| 仕事 | 普段の担当 | 人の分 |
|---|---|---|
| 会話からの教訓 | いつものエージェント | 普段の会話で訂正する |
| 教訓の差し込み先、範囲、完了 | 決定モデル。正解は結果から | 抜き取りと保留を確かめる |
| 止める検査 | 決まった規則。草稿はエージェント | 有効にするか決める |
| 作業の前と後の手順 | エージェント。組み込みの規則が確かめる | なし |
| 作業記録 | エージェントとサブエージェント | 読みたい時に画面で読む |
| 業務の正解 | 人 | 正解を付ける。エージェントが変えた聞き方の意味が違っていたら元に戻す |

[Andrej KarpathyのLLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)の考え方に沿い、原資料を残してエージェントが取り込み・検索・見直しを担います。詳しくは[hook](../../integrations/claude-code.ja.md)、[wikiの作法](../../skills/shikii/references/wiki.md)、[止める検査の作法](../../skills/shikii/references/guards.md)。

## 業務の判定を任せる

自分の仕事の判断（「この問い合わせは前のと同じ案件か」など）も、同じ仕組みで少しずつ任せられます。判定のファイルに質問・選択肢・入力・しきい値を書き（`shikii new`、または[既製の判定](../../decisions/README.md)を写す）、答えを付けていくと、ある自信より上なら当たると言える線が引けます。線が引けるまでは、全部が人に確かめる側に回ります。

cloneした中で（例の判定はインストーラーには入っていません）:

```sh
shikii new same-issue --from decisions/same-issue.yaml              # 例の判定を .shikii/decisions/ に写す
SHIKII_MODEL=local shikii up                                     # この例の問いは pii: true なので手元のモデルが要る。APIキーがあると up は SHIKII_MODEL=local の時だけ起こす
shikii decide .shikii/decisions/same-issue.yaml -i report1="…" -i report2="…" --local http://127.0.0.1:8080
#   → band=ask   （線がまだ無いので人が決める）
shikii serve --local http://127.0.0.1:8080                       # 答え合わせの画面: http://127.0.0.1:8095
#   正解が必要な数（eval.min_n）に届くと、線は自動で引かれる
shikii decide .shikii/decisions/same-issue.yaml -i report1="…" -i report2="…" --local http://127.0.0.1:8080
#   → band=act   記録付き: 何件の正解、何件を人が確かめ、act側の精度はいくつか
```

| 判断 | すること |
|---|---|
| `act` | 線の条件を満たしたので自動で進める |
| `ask` | 人に確かめる |
| `discard` | 動かない |
| `abstain` | 足りない入力か接続先を揃える |

線は質問とモデルの組ごとに持ち、どちらかが変われば測り直します。過去の案件の表(CSV)から正解を取り込む `shikii import` や、大きいモデルに同じ問いを聞き、人の正解とよく合う時だけその答えを正解に足す `shikii judge` もあります。`shikii tune` は貯めた正解で別の聞き方を採点し、`shikii drift` と `shikii check` はずれたモデルや弱められた線を捕まえます。APIキーやGPUなしで試すなら、cloneした中で `scripts/demo.sh` を実行します。

## 記憶はプロジェクトのもの

会話・教訓と原資料・仮採点・正解・線・止める検査・作業記録は、そのプロジェクトの `.shikii/` に入ります。関係ないプロジェクトとは分かれます。作業ツリーで作業しても、wikiと作業記録は元のプロジェクトのものを使います。プロジェクトの下に置いた作業ツリーでは、shikiiが自分で元のプロジェクトを見つけます。ほかの場所に作った作業ツリーでは、エージェントが元のプロジェクトを指定します。共通の `~/.shikii/agent` には雛形・道具・プロジェクトの一覧があります。`.shikii/` には私的な会話が入るので、初期化がGitの未追跡ファイルから除きます。

<p align="center"><img src="../assets/shikii-architecture.svg" alt="初期化したプロジェクトの .shikii/ に、エージェントが育てる知識(records・wiki・guards・handoff)と、判定を任せるための問い・正解・線を分けて持つ" width="100%"></p>

```text
.shikii/
  decisions/  決定モデルへの問いと、引いた線
  wiki/       教訓・条件・以前の版
  guards/     人の訂正から作った止める検査
  records/    会話・判定・採点・配送・観察・検査の結果と、教訓の原資料
  labels/     人と結果が付けた正解
  sessions/   セッションごとの控え(届けた教訓、伝えた知らせ、変わったファイル)
  handoff/    作業記録: 監査の報告、リリースの手順、差分、画像(画面で読む)
```
