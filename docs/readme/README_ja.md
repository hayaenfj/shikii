# shikii: 人は意図と正解だけを出す。聞き方も信頼も機械が育てる

## 目指すもの

**人が出すのは意図と正解だけ。聞き方も、信頼も、段階も機械が育て、育った知識は人のあいだで共有される。**

最近の AI には、文章を書くのではなく**選ぶ**ことに特化したもの（決定モデル）があります。「この依頼はファイルを書き換える依頼ですか？」と聞くと、「はい 0.92、いいえ 0.08」のように確率で答える。速くて安く、迷いが数字で見えます。

ところがその 0.92 はそのまま信用できません。AI が変われば意味が変わり、質問の文言を少し変えても変わる。作っている会社も「あなたのデータで確かめてから使ってください」と書いています。そして、確かめるには人が正解を付け、良い聞き方を人が考え、線を人が引き直す必要がある、というのが今の普通です。

shikii はそこを逆にします。人が持つべきものは 2 つだけ、**意図**（決めたいこと）と**正解**（起きた事実）。それ以外は技術で、技術は機械の仕事です。質問の文言、選択肢の説明、本文の並べ方。どこから上を信じるかの線（これを引く作業を**較正**と呼びます）。劣化の監視。文言やモデルが変わった時の引き直し。そして「この型の質問には、このモデルにはこう聞くと通る」という学びは、1 人の経験ではなく、証拠付きの共有の wiki に溜まります。

名前は「閾」（しきい）。確率に引く線のこと。コマンドの名前も `shikii`。

## 人がすること

| いつ | すること | どれくらい |
|---|---|---|
| 最初 | 決めたいことを質問に書く（`shikii new` が質問に答えるだけで作る） | 1 回 |
| 日々 | 「本当はどうだったか」を答える。画面のボタン 1 つ。結果から拾う仕組みを hook で組めば 0（同梱の例は Claude Code 用） | 1 件につき 1 回 |
| たまに | 機械が提案した言い換えが「まだ同じことを聞いているか」を見る。ボタン 1 つ | 提案が出た時だけ |

それ以外はありません。線を引く、引き直す、候補を作る、測る、劣化を見張る、記録を掃除する、は全部コマンドかサーバーが勝手にやります。

## まず一周する

Go 1.24 以上があれば、AI も API の鍵も無しで一周できます。

```sh
git clone https://github.com/hayaenfj/shikii && cd shikii && make build
scripts/demo.sh                 # 偽の AI で: 聞く → 正解を付ける → 線を引く → 検査 → 文言を変えて線が消える → 聞き直して戻る → 掃除
```

本物に向けるなら、この順です。

```sh
bin/shikii up                                   # 手元に Kev-4B を起こす(llama-server を探し、初回は約 2.5GB を取得、応答まで待つ)
bin/shikii new my-decision --type choice        # 質問にいくつか答えると decisions/my-decision.yaml ができる(この 1 枚を spec と呼びます)
bin/shikii serve --specs decisions --local http://127.0.0.1:8080   # http://127.0.0.1:8095/
```

基本構成は決まっています。実行する場所に `decisions/`（spec）、`wiki/`（聞き方の知識）、`.shikii/`（記録と正解）。置き場を選ぶ設定はありません。

聞き方の候補を AI に作らせたいなら、普通のチャット用モデルを載せた `llama-server` をもう 1 つ起こし（例: `llama-server -hf <チャット用の GGUF> --port 8087`）、`serve` に `--proposer http://127.0.0.1:8087` を足します。無くても、spec に自分で書いた候補は測れます。

あとはプログラムが `POST /v1/decide` を叩き（どの言語からでも）、人は画面で答え合わせをするだけ。

- 答えは `act`（自動で動く）/ `ask`（人に聞く）/ `discard`（捨てる）/ `abstain`（判定していない）の 4 つ。確率も付いてきますが、プログラムが分岐に使うのは帯です。「0.7 以上なら」のような数字をプログラムに書かせないため
- 答え合わせが spec の `eval.min_n` 件に届くと、サーバーが自分で線を引いて spec に書く。線が引けた（`act` の精度が足りた）あとは `act` が出る
- 画面の「聞き方」の欄で「AI に候補を 3 個作らせて測る」を押すと、裏で候補が作られ、溜まった正解で全部採点される。勝った候補が出たら「意味は同じ → 採用」を押す。これで新しい版と線が同時にできる

エージェント（Claude Code など）からは MCP（エージェントに道具を渡す共通の口）で、判定・答え合わせ・候補の採点までできます（`.mcp.json` が同梱）。採用だけは人の画面にしかありません。

```sh
bin/shikii doctor         # 何が動いていて何が足りないか、直すコマンドまで 1 画面で
```

## 機械が育てるもの

### 聞き方

正解率を動かすのは補正より文言です。手元の数字で、選択肢の説明を書き直しただけで 0.68 → 0.90、本文を答えの直前に置き換えただけで 27B のモデルが 0.919 → 0.968。

人が付けた正解は文言に依らないので、聞き方の候補をいくつ作っても**新しい正解なしで全部採点できます**。`shikii tune` は候補ごとに、正解率、確率の質、`act` で動いた時の精度（動いたうち正しかった割合）と再現率（正しいもののうち動けた割合）を出します。

さらに「候補を選ぶこと自体がまぐれでないか」を測ります。正解を 5 つに分け、4 つで候補を選び、残りの 1 つで測る（holdout）。これを 5 回。採用するのは、その測りが「今の文言のまま」を上回り、しかも上回り方が偶然では説明できない時だけです（候補と現状で正誤が食い違った行を数え、片側の符号検定で p < 0.05）。候補を 20 個足しても、同じ実力なら採用される確率は 5% を超えません。62 件中 1 件多く当てた程度では通らず、手元でも実際に通りませんでした（[wiki のパターン](../../wiki/patterns/other-is-not-a-request.md)に記録）。

候補は人が書いてもよく、チャット用の AI に作らせることもできます（`--propose`）。AI には、今の聞き方、どこで間違えているか、外した実例、そして [wiki](../../wiki/index.md) の該当ページを渡します。該当ページとは、この型の聞き方、このモデルの系統の癖、確認済みのパターン、この判定の決まりと過去の学びです。wiki は実行する場所の `wiki/` にある markdown のフォルダで、`runs/` と `specs/` の run の記録は機械が書き、型・モデル・パターンのページは人が書きます。結果は `runs/` に数字と採否と一行の学びとして残り、次の提案がそれを読みます。

外に出せない本文は提案役にも出しません。`pii: true` の判定と、本番のデータに触った作業で記録した本文は、手元（127.0.0.1）の提案役にしか見せません。提案役に鍵が要るなら環境変数 `SHIKII_PROPOSER_KEY`。ホスト版の決定モデルの鍵は提案役には渡しません。

ただし**意味は機械には確かめられません**。言い換えが「まだ同じことを聞いているか」は人が画面で確認し、「違う」と言えばそれも記録されます。数字は機械、意味は人。

### 信頼

- 線（較正）は「質問文・選択肢・本文の型を 1 つにまとめた指紋（ハッシュ）」と「AI が名乗った名前」の組ごとに引く。どちらかが変われば線は消え、答えは `ask` に落ちる。古い根拠で勝手に動くことはない
- 消えた線を戻すのは機械の仕事。正解は本文と一緒に残っているので、`calibrate` が新しい組み合わせで全部聞き直す。人は要らない
- 確率を直すかどうかも数字で決める。型ごとに 2 つの方法（そのまま使う、確率を直す式を当てる）を、正解を 5 つに分けて「4 つで学び、1 つで試す」を 5 回やって比べ、`act` の精度を満たす中から選ぶ。「較正済み」と謳うモデルでも同じ
- `check` は CI（コードを変えるたびに自動で回る検査）で、文言が変わった線・手書きの線・精度が足りない線を落とす。`drift` は最近の正解で劣化を見る
- **抜き取り検査**: 機械が `act` で自動で動いた判定は人が見ないので、そのままだと `act` の精度は人の正解で測れない。そこで 20 件に 1 件を答え合わせの画面に出し（判定の番号で決まるので何度見ても同じ 1 件）、人が確かめた分だけでも精度を測る。機械が作った正解（上の段の答え、聞き直し）でいくら良く見えても、人が確かめた `act` の判定が `min_n` 件以上あって精度が `act` に届かなければ `check` が落とす
- 安全に関わる分岐は、**わざと壊してテストが落ちるのを見てから直した**記録を運用メモと各手引きに残しています。Go のテストは 8 パッケージ 138 本

### 段階（段がそろった）

モデルを増やすのではなく、聞き方に段を作ります。まず最小の質問、迷えば文脈を足して同じ質問を聞き直し、それでも迷えば人。

- **最小の質問**: spec の `state.template`。今までどおり
- **文脈を足す**: spec に `state.context` を書く（たとえば直前のやりとり `{{ previous }}` を足した並べ方）。`decide` は最小の質問の答えが迷っていて（`ask` 帯。多択ではどの選択肢にも届かない `discard` も）、呼ぶ側が文脈の入力を渡していた時だけ、同じ質問を文脈付きで聞き直します。文脈付きの聞き方は別の指紋なので、線（較正）も別に引かれ、線ができるまで `act` は出ません。文脈が渡されなかった時、最小の質問で確信できた時は何も起きないので、`state.context` を足しても今まで大丈夫だった判定の費用は増えず、最小の質問の指紋と線もそのままです
- **人**: どの段でも `ask` のまま残った判定が答え合わせの画面に並びます

実機（27B を `shikii-readout` で、線なし）で、短い返事に直前のアシスタントの発言「`--legacy` フラグを消しましょうか？」を足した時:

| 本文 | 本文だけ | 直前の発言を足す |
|---|---|---|
| do it | operation 0.58（どれにも届かない） | change_request 0.73 |
| yes please | question 0.34（どれにも届かない） | change_request 0.87 |
| go ahead | other 0.32（どれにも届かない） | change_request 0.77 |
| the tests | question 0.58（どれにも届かない） | change_request 0.45（まだ迷う → 人へ） |

文脈で決まるものは決まり、本当に曖昧なものは人に残る。それが狙いです。

正解は段を下りていきます。文脈を足した段で `act` に届いた答えは、最小の質問の正解として残ります（出どころ `context`、重みは較正済みの確率）。人が答えると、その判定が通った全部の段に同じ正解が付きます。`calibrate` は段ごとに線を引き、`check` は両方を検査し、`status` は「最小の質問で決まった / 文脈で決まった / 人に回った」の数を **1000 判定あたりの人の判断** として出します（「人に回った」は段を上げる時と同じ規則で、`ask` と、多択では `discard` も）。線を書くのは人が決めた正解が `min_n` 以上ある時だけで、機械の正解だけでは引きません。聞き直しも機械の正解は聞き直さないので、機械の答えが人の正解に化けることはありません。これが段階の進み具合の物差しです。`tune` は聞き方の候補を最小の質問の段だけで採点するので、候補が持っていない文脈の手柄を数えることはありません。

分解もあります。多択の質問を **はい/いいえ の列** に割る候補（spec の `steps:`）を書くか AI に提案させると、`tune` が他の候補と同じ貯金で採点します。各段の答えの確率を掛け合わせて元の選択肢の分布を作るので、正解はそのまま使え、較正も帯も同じです。全段を 1 回の呼び出しに載せるので、本文を読む費用は 1 回分のまま。効くのは、多択は下手でも はい/いいえ なら当たるモデルの時です。多択が上手な 27B では分解が負けました（0.790 対 0.968）。それも tune が同じ貯金で測って教えてくれます。

## どの AI が使えるか

決定モデル向けの共通の呼び方（`POST /v1/systemone`）を話すものなら何でも。話さない普通のチャット用モデルは、付属の変換役 `shikii-readout` を前に置きます。手元でモデルを動かす定番の道具 llama.cpp の、改造していない版だけで動きます。学習も要りません。GGUF はそのモデルのファイル形式です。

| つなげる先 | 要るもの |
|---|---|
| **手元の決定モデル**（Kev-4B、OpenJev、Clef、…）を llama.cpp で | `shikii up`（または `llama-server -hf ggml-org/Kev-4B-GGUF:Q4_K_M`）。llama.cpp 0.6.0 以上 |
| **普通のチャット用モデル**（GGUF）を `shikii-readout` で | `shikii up --gguf <file>` が自動で変換役を前に立てる。本家 llama.cpp 0.7.0 |
| **TypeSafe Jev**（ホスト版） | 環境変数 `TYPESAFE_API_KEY` |
| **OpenRouter Decisions API** | `DECISIONS_API_KEY`、`--hosted https://openrouter.ai/api/alpha/decisions` |
| **PrismML Bonsai** を [BonJev](https://github.com/ChezRD/bonjev) で | Rust のビルドと Prism 版の llama.cpp。[`integrations/bonjev.md`](../../integrations/bonjev.md) |
| **偽の AI**（`bin/fake-systemone`） | 何も要らない。デモとテスト用 |
| **Claude Code の hook**（claude-jev） | [`integrations/claude-code.md`](../../integrations/claude-code.md) |

本文を外に出してよいかは、あなたが決めます。spec には送ってよい先を `send_to` に書きます。`pii: true` は「本文に個人情報が入り得る」の印で、`send_to` に何が書いてあっても外の AI には送りません。`pii: false` なら `send_to` のとおり。既定は無く、必ずどちらかを書きます。本番のデータに触った作業中は `--tainted` を付けます。その本文は、後の聞き直しでも、聞き方の採点でも、提案役への実例でも、手元の外には出ません。

## 実際に測った結果

同じ質問、同じ正解で 4 つの AI を比べました（表に無い 5 つ目、Bonsai 2 を改造版の変換役で読んだものを含めると、はい/いいえ の 2 題材 × 5 で 10 通り）。題材は全部作り物: 依頼文の種類あて（英語 39 件・日本語 23 件）、不具合報告の重複判定（日本語 32 組）、問い合わせの同一判定（日本語 32 組）。全表は [`docs/model-comparison.md`](../model-comparison.md)。

| AI | ライセンス | 正解率（全体 / 日本語） | はい/いいえ の確率の質、生 → 補正後（小さいほど良い） | 1 問の秒数 |
|---|---|---|---|---|
| Kev-4B（専用に学習された決定モデル） | Apache 2.0 | 0.919 / 0.913 | 0.038 → 0.035 / 0.030 → 0.020 | 0.25 |
| OpenJev 27B（同） | CC BY-NC 4.0 | **0.984 / 1.000** | **0.007** / 0.037（補正なし） | 3.8 |
| Bonsai 2 27B を BonJev で | Apache 2.0 | 0.968 / 1.000 | 0.049 → **0.019** / 0.084 → 0.028 | 2.5 |
| **Ternary-Bonsai-27B を `shikii-readout` + 本家 llama.cpp で** | Apache 2.0 | 0.968 / 1.000 | 0.048 → 0.024 / 0.033 → 0.020 | **0.58** |

分かったことを 3 つ。

**文言のほうが補正より効く。** 間違い 21 件のうち 19 件が「その他」に落ちていた質問は、選択肢の説明を書き直しただけで 0.68 → 0.90。補正はその後の「順番は合っているが自信が足りない」にだけ効きます。

**補正が要るかどうかは、触れ込みではなく数字で決まる。** OpenJev は生の確率で足りて 2 回とも「補正なし」、Kev-4B はわずかに補正が勝ち、普通のチャット用モデルは 1.5〜4 倍良くなった。10 通り全部で正と負はきれいに分かれていて、違いは確率の正直さだけ。

**普通のモデルが、専用モデルの隣に並んだ。** 27B のチャット用モデル、本家 llama.cpp、変換役が 1 つ。改造も再学習も Rust も要らず、Apache ライセンスで最良の経路（Bonsai 2 を BonJev で）と同じ正解率、専用に学習された 4B より上、日本語は全問正解、1 問 0.58 秒。

これは**仮説**で、まだ主張ではありません。型の付いた判定なら、測った聞き方と較正の組は、同じ土台のモデルで、微調整（LoRA）よりずっと少ない例で使える精度に届くかもしれない。検索で文脈を足す方法（RAG）より確率が正直かもしれない。確かめ方はこのリポジトリにあります。同じ課題、同じ正解、同じモデルで 3 つの方法を並べ、正解率と確率の質を比べます。最初の測定では支持されませんでした。1 課題 62 件、土台を Qwen3-4B に揃えると、約 50 件の LoRA が top-1 0.952、測った聞き方が 0.855、似た例を足す方法が 0.855（Brier はこちらが良い）。同じ重みで prompt の配置だけで 13 ポイント動いたので、次は配置を `tune` の候補に入れます。3 つの腕は `scripts/bench/` で回り、数字と注意は [docs/bench.md](../bench.md) にあります。

## よくある質問

**結局、人は何をするのですか。** 最初に決めたいことを書く。日々は画面のボタンで「本当はこうだった」を答える（結果から拾う hook を組んだ判定なら 0 回）。機械が言い換えを提案したら「意味は同じ」か「違う」を押す。それだけです。

**なぜ `act` にならないのですか。** その質問とその AI の組み合わせで、まだ線が引かれていないからです。正解が `eval.min_n` 件に届けばサーバーが自分で引きます。画面に「集めている n/50」と出ます（端末の `shikii status` では `collecting (n/50)`）。

**質問を変えたら線が消えました。** 正しい動きで、かかるのは計算だけで、人の手は要りません。もう一度 `calibrate --write` を回すか、画面で候補を採用すれば、残っている正解を新しい文言で聞き直して線が戻ります。

**AI に聞き方を変えさせて大丈夫ですか。** 採用には 3 つの条件が全部要ります。溜まった正解での数字で勝つこと。選び方を別の正解で試した結果（holdout）が「今のまま」を上回り、その差が偶然では説明できないこと。そして人の「意味は同じ」。端末の `tune --write` でも、AI が今作った文言はその場では採用されず、人が読んでからです。却下した理由は wiki に残り、次の提案役がそれを読みます。

**データはどこに送られますか。** AI に見せる本文だけが `send_to` に書いた先へ行きます。何が個人情報かを shikii は推測せず、`pii: true/false` をあなたが書きます（`true` なら外には送らない）。判定の本文は常に手元の記録に残るので、人が答えられ、聞き直しもできます。鍵は環境変数からだけ読み、キーチェーンには触りません。

**どのモデルを使えばいいですか。** ライセンス・速さ・言語で決まることで、shikii は決めません。上の表と `scripts/eval-model.sh <url> <name>` で、新しい AI でも同じ表が作れます。

**記録が増え続けます。** `shikii gc` が、30 日より古くて正解の付かなかった記録を消します。正解付きの記録と正解は線の材料なので残ります。`--apply` を付けるまでは数えるだけ。

コマンド一覧（フラグは位置引数の前でも後ろでも書けます）:

```
shikii new       <id> [--type choice|noul|score] [--question ...] [--option id=desc ...] [--from spec.yaml]   # 質問に答えて spec を作る
shikii up        [--hf repo:quant | --gguf file --alias name] [--port 8080]   # 手元のモデルを起こす。普通の GGUF なら変換役を前に
shikii serve     [--port 8095] [--specs DIR] [--store DIR] [--local URL] [--proposer URL]   # HTTP の口 + 答え合わせと聞き方の画面
shikii mcp       [--specs DIR] [--store DIR] [--local URL] [--proposer URL]   # 同じものを MCP の道具として(採用の道具は無い)
shikii doctor    [--specs DIR] [--store DIR] [--local URL] [--hosted URL]   # 何が動いていて何が足りないか
shikii decide    <spec> -i k=v ... [--hosted URL] [--local URL] [--tainted] [--json]   # 聞く(プログラム向け)
shikii label     <trace_id> <truth> | --last --spec-id ID <truth>   # 正解を付ける(端末から)
shikii calibrate <spec> [--labeled file] [--model M] [--write]   # 線を引く。古い正解は新しい文言で聞き直す
shikii tune      <spec> [--propose N --proposer URL] [--write]   # 聞き方の候補を採点。holdout と符号検定が勝ち、人が確かめた候補を新しい版に。結果は wiki/runs/ へ
shikii check     <spec>... [--store DIR]   # CI: 文言が変わった線、手書きの線、精度不足の線を落とす
shikii drift     <spec> --model M [--window N]   # 最近の正解で劣化を見る
shikii bias      <spec> [--rows K] [--permutations N]   # 選択肢の順番で答えが変わるか
shikii status    [spec...] [--store DIR]   # 記録・正解・線の溜まり具合
shikii gc        [spec...] [--older-than 30d] [--apply]   # 古くて正解の無い記録を消す(既定は数えるだけ)
shikii hash      <spec>
```
