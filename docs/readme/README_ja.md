# shikii: 問いと正解を資産にする。モデルは使い捨て、知識は自分で育つ

### AI の判定（はい/いいえ、どれ、どの程度）を業務で使い続けるための道具。人が出すのは、意図と、抜き取りの正解と、主張の意味の確認だけ。

**AI は「たぶん 0.9」と言う。shikii は「その 0.9 で動いていいか」を根拠付きで答え、聞き方を自分で良くし、学んだことを検証できる主張として wiki に残す。モデルを替えても、問いと正解と主張はそのまま使える。**

> [!IMPORTANT]
> shikii は推論そのものは行いません。手元やホスト版のモデルに質問を送り、答えを記録し、答え合わせが済むまで「自動で動いてよい」とは言いません。
> 「動いてよい」の根拠の数字も、聞き方の候補も、wiki の主張の証拠も、機械が測って書き込むもので、人が手で書くものではありません。状態（この主張は確かか）を決めるのだけが人です。

## 目指すもの

**問いと正解を資産にする。モデルは使い捨てで、知識は検証できる主張として wiki に溜まり、測るたびに自分で育つ。人が出すのは意図と、抜き取りの正解と、主張の意味の確認だけ。**

最近の AI には、文章を書くのではなく**選ぶ**ことに特化したもの（決定モデル）があります。「この依頼はファイルを書き換える依頼ですか？」と聞くと「はい 0.92、いいえ 0.08」のように確率で答える。速くて安く、迷いが数字で見えます。普通のチャット用モデルも、`shikii-readout` を前に置けば同じ口で答えます。

ところが業務で使い続けるには、確率だけでは足りません。0.9 が本当に 9 割当たるのか、モデルを替えた瞬間に嘘にならないか、聞き方を 1 語変えたら何が起きるか、誰も見ていない自動の判定が正しいまま走っているか。それを人が毎回確かめるなら、AI を使う意味が薄れます。

shikii は、その確かめる仕事を機械に渡し、人の仕事を 3 つに絞ります。

1. **意図を書く**: 何を、どの選択肢で判定したいか（spec）。質問に答えるだけで作れます
2. **抜き取りの正解に答える**: 機械が迷った判定と、自動で動いた判定の 20 件に 1 件。画面でボタンを押すだけ
3. **主張の意味を確かめる**: 機械が「この聞き方の方が当たる」と測って下書きした主張を、人の言葉で一般化し、確かか決める

残りは機械がやります。確率を直す線、聞き方の候補の採点と採用、文脈を足す段、別のモデルへの乗り換え、学んだことの記録。

## 何が違うか

<p align="center"><img src="../assets/shikii-architecture.svg" alt="shikii の構造: 人がすること 3 つ、資産(問い・正解・領収書)、機械が育てる輪、検証できる wiki、使い捨てのモデル" width="100%"></p>

**1. 検証できる wiki。** 「聞き方」の知識は文章ではなく、**主張 + 効く範囲 + 証拠 + 再検証の手順**として溜まります。`shikii wiki verify` が主張を今のモデルで測り直し、証拠を足し、独立したモデル 2 つが支持すれば「確かにできる」と印を付けます。状態を変えるのは人だけ。tune が勝った候補を見つけるたびに主張の下書きが生まれ、別のモデルで測るたびに証拠が厚くなる。別の人が自分のモデルで同じ主張を回せば、その結果も証拠になる。文章の wiki は読んで更新されますが、こちらは**測って昇格・降格します**。

**2. 問いと正解は資産、モデルは使い捨て。** 知識を重みに入れる（微調整）と、モデルを替えた時に全部やり直しです。shikii は知識を**問いの側**（文言、選択肢の説明、配置、分解、文脈、似た例の引き方）と**正解の貯金**に置きます。モデルを替えたら、`calibrate` が貯金を聞き直して線を引き直すだけで、人の手は 0。ベンチでは、文言と配置を機械が選び、似た例を足した聞き方が、約 50 件の LoRA と同じ正解率に届きました（下の表）。

**3. 決定ごとに領収書。** 自動で動いた判定には、どの線を、いつ、何件の正解で引いたか、そのうち人が確かめた分と、その精度が付きます。「95% の確信」ではなく「この種の判定は人が検査した 48 件で精度 0.96」と言える。審判（別の大きいモデル）に正解の多くを出させる時も、人の正解との一致率を先に測り、届いた審判だけを使い、人の精度には数えません。

## 最短の入り口

- **Docker**: Go もモデルの準備も無いなら `docker compose up`。llama.cpp（Kev-4B）と shikii が立ち、答え合わせの画面が http://127.0.0.1:8095 に出ます。`decisions/`、`wiki/`、`.shikii/` はホストのまま（[integrations/docker.md](../../integrations/docker.md)）
- **Claude Code / Cursor**: `.mcp.json` に 3 行足すと `shikii_decide` / `shikii_label` / `shikii_tune` が道具として使えます。この repo は Claude Code の plugin でもあり、skill（`skills/shikii/SKILL.md`）がエージェントに「いつ判定を呼ぶか、帯にどう従うか、正解と状態は人のもの」という作法を教えます
  ```json
  { "mcpServers": { "shikii": { "command": "shikii", "args": ["mcp", "--specs", "decisions", "--store", ".shikii", "--local", "http://127.0.0.1:8080"] } } }
  ```
- **端末**: 既製の判定（[`decisions/`](../../decisions/README.md) の 6 つ。依頼の種類、不具合の重複、問い合わせの同一判定、…）をそのまま使うか、`shikii new --from decisions/prompt-intent-v2.yaml` で写して書き換える
  ```sh
  make install && shikii up                       # 手元のモデルを起こす(Kev-4B を自動で取る)
  shikii decide decisions/prompt-intent-v2.yaml -i message="fix the typo" --local http://127.0.0.1:8080
  shikii serve --specs decisions --store .shikii --local http://127.0.0.1:8080   # 答え合わせの画面 http://127.0.0.1:8095
  ```
- 過去の判定の表があるなら `shikii import past.csv --spec decisions/<id>.yaml` で正解の貯金にできます。最初の線を引く 50 件を手で答えなくてよい。CI では `uses: hayaenfj/shikii@main` が PR ごとに `shikii check` を回します

基本構成は、実行する場所に `decisions/`（判定）、`wiki/`（知識）、`.shikii/`（記録と正解）。置き場所のオプションはありません。

## 人がすること

答え合わせの画面（`shikii serve`）は、IT に詳しくない人が迷わないように作っています。

- 判定ごとのタブ。開くと人の言葉の質問、「AI は迷いました / 自分で動きました」、「AI の予想: 変更の依頼（自信 82%）」、答えのボタン。1〜9 のキーと Enter（AI と同じ）で流せます
- 既定は 1 件ずつ。一覧にも切り替えられ、「AI が迷った / 抜き取り / その他」の数を押して絞れます。あとで答えたいものはスキップ
- 「まだ学習中: 答え合わせ 12 件。AI が自分で動けるようになるまで 50 件」の進み具合。揃えば「AI が自分で動いてよい状態です」
- 「くわしく」を押すと、主張と下書きの欄（下書きを一般化して主張にする、確かだと決める、却下する）、聞き方の候補、指紋やモデル名が出ます

人が書くものは 2 つだけ。spec（意図）と、wiki の細則（「短い依頼も依頼」「同じ画面の別の不具合は違う」のような、その判定の決まり）。細則は人が正解を付ける時の手引きで、審判が読む手引きでもあります。

## 機械が育てるもの

### 聞き方

同じ正解の貯金で、聞き方の候補を全部採点します（`tune`）。候補は文言、選択肢の説明、入力の並べ方、**配置**（`layout: plain` など、変換役がどう並べるか）、**分解**（多択を はい/いいえ の列に）。人が書いても、AI に提案させてもよい。採用の門は 2 つ: 貯金を 5 つに分けて選び直す holdout が現状を上回り、対の勝敗の符号検定で p ≤ 0.05。そして人が「意味は同じ」と確かめる。勝った候補は wiki の主張の下書きになります。

配置が候補になったのは、同じ 4B の重みが配置だけで 13 ポイント動いたからです。候補にしたら、tune は自分でそれを選びました。人がしたのは候補を 2 行書くことだけ。

### 信頼

- 線（較正）は「問いの指紋 × モデル名」ごと。1 語変えれば線は消え、答えは `ask` に落ちる。戻すのは機械（貯金を聞き直す）
- 線を書けるのは、人が決めた正解が `min_n` 件以上ある時だけ。機械の正解（上の段の答え、審判）だけでは引けない
- 抜き取り: 自動で動いた判定の 20 件に 1 件を人に見せ、人の正解だけでの精度を測る。`check` は CI でそれを守る
- 領収書: `act` の判定ごとに、線の方法と日、正解の数と人の分、人が確かめた act の判定の数と精度
- 審判: `shikii judge` が別の大きいモデルに同じ質問をし、人の正解との一致率が `act` に届く時だけ、答えの無い判定に重み付きの正解を付ける。審判も迷えば人へ

### 段階

モデルを増やさず、聞き方に段を作ります。最小の質問 → 迷えば文脈を足して聞き直す（spec の `state.context`。別の指紋、別の線）→ それでも迷えば人。上の段で確信した答えは下の段の正解になり、人の答えは通った全部の段に付く。進み具合は `status` の「1000 判定あたりの人の判断」。

### 知識

tune の run が終わるごとに、現状に有意に勝った候補が主張の下書きになり、その spec についての既存の主張には run の採点が証拠として足されます。人は下書きを一般化した文に書き直して主張にし、確かだと決めるか却下する。`shikii wiki verify` で主張を今のモデルで測り直せます。構造の全体は [docs/architecture.md](../architecture.md)。

## 測った結果

同じ課題（依頼の種類、62 件）、同じ土台 Qwen3-4B、3 つの方法。手順と注意は [docs/bench.md](../bench.md)。

| 方法 | top-1 | Brier |
|---|---|---|
| 測った聞き方（tune が配置 plain を選ぶ） | 0.903 | 0.0959 |
| 似た例 5 件を本文に足す（配置 plain） | 0.952 | 0.0482 |
| LoRA 約 50 件 × 5 分割 | 0.952 | 0.0375 |

「文言と較正だけで微調整に届く」という当初の仮説は、この課題では支持されませんでした。文言と配置を機械が選び、似た例を足すと正解率では並び、確率は LoRA が良い。はい/いいえ の課題（32 件）では向きが逆で、約 26 件の LoRA は土台そのままより悪く、似た例を足す方法は効きました。微調整が勝つかは型と例の数で変わる、が今の正直な答えです。

27B（Ternary-Bonsai、変換役越し）では現状の文言で 0.968、配置 plain で 0.984、分解は 0.790。配置の差は 1 件分で門を越えず現状維持。これも tune が同じ貯金で測って教えてくれました。

## どの AI が使えるか

決定モデル向けの共通の呼び方（`POST /v1/systemone`）を話すものなら何でも。話さない普通のチャット用モデルは、付属の変換役 `shikii-readout` を前に置きます。本家の llama.cpp だけで動き、学習は要りません。

| つなげる先 | 要るもの |
|---|---|
| **手元の決定モデル**（Kev-4B、OpenJev、Clef、…）を llama.cpp で | `shikii up`（または `llama-server -hf ggml-org/Kev-4B-GGUF:Q4_K_M`） |
| **普通のチャット用モデル**（GGUF） | `shikii up --gguf <file>` が変換役を前に立てる。配置は `layout:` で tune の候補にできる |
| **ホスト版**（TypeSafe Jev、OpenRouter Decisions） | 鍵を環境変数で。`pii: true` の本文と、本番データを読んだセッションの本文は送られない |

比較表は [docs/model-comparison.md](../model-comparison.md)。

## よくある質問

**正解を 50 件も集められない。** 過去の表があれば `shikii import`。無ければ審判（`shikii judge`）に大きいモデルで出させ、人は抜き取りで検査する。それでも線が引けるまでは `act` は出ません。それが正しい挙動です。

**モデルを替えたらどうなる？** 線は消え、`ask` に戻ります。`calibrate` が貯金を聞き直して線を引き直す。人は要りません。問いと正解と主張は残ります。

**聞き方を自分で直したい。** spec の `variants:` に候補として書いてください。本体を直接書き換えると線が消えるだけで、良くなったかは分かりません。tune が測り、人が意味を確かめ、採用すれば新しい版になります。

**wiki の主張が間違っていたら？** 証拠が反証を積めば verify が「contradicts」と記録します。却下は人が画面で押す。主張は消さず、却下した記録として残します。

**本文を外に出したくない。** spec の `pii: true`。手元のモデルにしか送られず、提案役も審判も手元に限られます。

**自分のプログラムから使いたい。** `shikii serve` の HTTP（`/v1/decide`、`/v1/label`）、MCP、CLI の `--json`。

## 手伝ってくれる人へ

- 安全に関わる分岐は、**わざと壊してテストが落ちるのを見てから直す**。通るだけのテストは何も示しません。Go のテストは 8 パッケージ 161 本
- 数字は全部スクリプトから出す。run の記録は不変で、文書の数字は run を指す
- wiki の主張の状態を変えるのは人だけ。機械は証拠を足し、confirmable と言うだけ
- 新しいオプションは足さず、基本構成と固定の規則で決める
