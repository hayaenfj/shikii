# shikii とメモリーの違い

## ひとことで言うと

「前に話したことを覚えておく」ところは、ChatGPT や Codex のメモリーと同じです。shikii は、その先で次の 3 つをします。

1. **覚えたことを、必要な場面でエージェントに届けます。** 依頼を始める前や、ファイルを変える直前に、関係する知識を渡します。
2. **届けた知識が役に立ったかを振り返り、知識を直します。** 役に立たない知識は届けるのをやめ、間違っていれば出典を確かめて直します。
3. **AI に任せてよい範囲を、実際の結果から決めます。** あなたの答えや確かめられた結果と AI の判断を比べ、AI だけで決めてよい場面と、あなたに確認する場面を分けます。

目的は、同じ説明や訂正を何度も繰り返さなくてよくすることと、プロジェクトに合った働き方を育てることです。

## 例: 「説明書は日本語版と英語版を一緒に直して」と伝えた場合

メモリーは、この言葉を覚えて、次の会話の参考にします。ただ、実際に両方を直したかまでは分かりません。

shikii では、次のように扱います。

- この決まりを、いつ使うかと出典(あなたがいつ何と言ったか)を付けた記事として保存します。
- 説明書を直す作業の前に、その記事をエージェントに届けます。
- 作業の後、エージェントはその記事が役に立ったかを振り返って記録します。
- 「両方のファイルを変えたか」のように機械で確かめられる部分は、あなたが有効にした検査で、作業の終わりに確かめます。片方しか直していなければ、エージェントは作業を終えられません。

## 比べると

| | メモリーでできること | shikii が加えること |
| --- | --- | --- |
| 覚える | 前の会話の文脈、好み、プロジェクトの慣習を覚える | 使う場面と出典を付けて、記事として残す |
| 使う | 次の会話や作業の参考にする | 依頼の前やファイルを変える直前に、関係する記事を届ける |
| 守らせる | 必ず守らせたい指示は `AGENTS.md` などに書くよう案内されている | 機械で確かめられる決まりを、作業の終わりに検査する |
| 直す | 覚えた内容を見たり消したりできる | 役に立ったかの振り返りをもとに、届けるのをやめたり、記事を直したりする |
| 任せる | 覚えた文脈を踏まえて答える | AI の判断と実際の答えを比べて、AI だけで決めてよい範囲を決める |
| 共有する | アプリごとに保存先と設定がある | 同じプロジェクトにつないだ Claude Code・Codex・OpenCode で、同じ知識を使う |

## shikii の中で回っている 2 つの流れ

### 1. 知識を使って、手入れする

1. **残す。** あなたが伝えた目的、選んだ方針、訂正、確かめた結果を、プロジェクトの `.shikii/` に保存します。記事には「どんな時に使うか」と出典があり、後から理由を確かめられます。
2. **届ける。** 仕事の始めや、関係する操作の前に、必要な記事をエージェントに渡します。
3. **振り返る。** エージェントは、届いた記事が実際の行動にどう影響したかを記録します。「届いた」「作業が成功した」だけでは、役に立ったとは数えません。
4. **直す。** 同じ場面で何度も使われなかった記事は、その場面へ届けるのをやめます。間違いや古くなった所は、出典を確かめて直します。あなたも画面から記事を編集・削除できます。

似た依頼の前に示すあなたの過去の回答も、同じように扱います。2 回以上使われず、一度も役に立っていない回答は示さなくなり、画面の知識欄の「AI が無効と判断した過去の答え」に並びます。この判断は、画面の「元に戻す」で取り消せます。

この流れの上に、次のことも積み重ねています。

- 作業の途中で分かったことを、同じ作業の記録に足せます。
- 前に使った手順は、そのときの条件・失敗・直し方と一緒に読み、今回の条件と比べます。前の成功を、そのまま今回の成功とは見なしません。
- 知識が届かなかった時は、その理由(検索に合わなかった、すでに届いていた など)を当時の記録から調べ、記事を直してから、過去の場面で試せます。
- 複数のエージェントで作業する時は、ひとりの発見をほかの担当に届け、別の条件で確かめて、同じ知識に戻せます。調査・実装・確認と担当が替わっても、確かめた条件と残る疑問を引き継ぎます。
- どれだけ読めば足りるかや、調査の進め方も、実際の結果から選び直します。別の 2 つの仕事で確かめてから採用し、悪くなったら前のやり方に戻します。

### 2. 判断を測って、任せ方を変える

- 「この依頼は終わったか」のように繰り返す判断について、AI が出す確率と、あなたの答えや実際の結果を比べます。
- 十分な記録がたまり、AI の自信と当たる割合が合っていれば、「ここより上なら AI だけで進めてよい」という線を引きます。線が引けるまでは、自動では進みません。

育つのはプロジェクトの知識と判断の基準です。AI 本体を学習し直すわけではありません。

## できないこと・言えないこと

- 振り返りはエージェントによる評価です。あなたの答えや、性能が上がったという測定結果とは分けて保存します。
- 知識をたくさん読んだことは、仕事が良くなった証拠にはなりません。
- 検査が確かめられるのは、機械で調べられる部分だけです。たとえば「両方のファイルを変えたか」は確かめられますが、文章が分かりやすいかまでは保証しません。
- 知識や AI の判断は、操作の許可にはなりません。今の依頼と、エージェントの権限の設定が優先されます。
- 速く・軽くした変更は、shikii が知識を渡す量や読む回数を減らすものです。モデル全体の応答時間や回答の品質が上がったという意味ではありません。

## OpenAI のメモリーについて(比べた範囲)

OpenAI の公開説明では、メモリーは好みだけでなく、繰り返す作業やプロジェクトの慣習など、前の会話の文脈を次の仕事へ持ち越すものです。ChatGPT のメモリーと Codex のローカルメモリーは、別の保存先と設定を持ちます。Codex のローカルメモリーには、前の会話をもとにした要約や出典も含まれます。そのため、「OpenAI は好みしか覚えない」「shikii だけが手元に保存する」という分け方は正確ではありません。

OpenAI も、必ず守らせたいチームの指示は `AGENTS.md` などに書き、メモリーだけに頼らないよう案内しています。

ここで比べたのは、2026 年 11 月 10 日に確かめたメモリー機能の公開説明です。OpenAI の製品全体の指示・ツール・権限の仕組みとの比較ではありません。([メモリーの説明](https://learn.chatgpt.com/docs/customization/memories)、[パーソナライズの説明](https://learn.chatgpt.com/docs/personalize))

## 記憶の方針が変わる更新

記憶の扱い方が変わる版に更新すると、エージェントが既にある知識の見直しを始めます。その間は「Upgrading memory…」と進み具合が表示されます。元の出典、あなたが伝えた好み、過去の判断は残したまま、古い手順の訂正や重複の整理を少しずつ進めます。読んだだけでは見直し済みにせず、出典が足りない所は未解決のまま残します。一度見直しが済めば、同じ方針の普通の更新で最初からやり直すことはありません。

## 各版の振り返り

版ごとに、何を加えたかと、その時に考えたことを残しています。古い順です。表の 1 行より詳しく、変更履歴より使う側から見た説明です。

### 0.17では、知識を使えなかった理由から手入れへ進める

たとえば、日英の説明書を一緒に直すという記事があるのに、ある更新作業では届かなかったとします。shikiiでは、エージェントが次の流れで改善できます。

1. **理由を調べる。** 当時の記録から、検索に一致しなかったのか、すでに届いていたのか、過去の評価や判定モデルによって除外されたのかを確認します。今の検索結果から過去を推測しません。
2. **必要なところだけ直す。** 適用条件が実際の作業を表していなければ、出典と変更理由を添えてその文章だけを直します。別の編集が入っていれば保存を拒否し、他の節や履歴を上書きしません。
3. **保存前に試す。** 修正案を過去の場面に当て、候補に入る記事がどう変わるか、別の記事を押し出さないかを比べます。後から増えた記事を過去の比較に混ぜません。

これは、知識が届かなかった時に、利用者が同じ説明をする前にエージェントが原因を調べられる仕組みです。例題の入力や比較結果の採点を利用者に求めません。

比較が確かめるのは**検索候補の変化**です。配信の抑制や判定モデルは再実行せず、実際に届く・役立つと保証するものではありません。記事や評価、人の正解も保存しません。診断記録は最大32件・4MiBを保持し、記録のない過去や不完全な記録は比較できないと明示します。実際に役立ったかは、その後の仕事で別に振り返ります。

### 0.18〜0.20では、知識を作業中に使い、結果を次へ戻す

仕事を始めた時の記憶だけでは、途中で分かった条件や、試してうまくいかなかったことが次の仕事へつながるとは限りません。shikiiでは、過去の知識を使うところと、今回の経験を残すところを同じ作業の記録でつなげます。

1. **作業案を照合する。** 過去の判断理由や見送った案、適用条件を読み、今回の案に合うかを考えます。繰り返す仕事では、出典のある手順を今回の条件に合わせて組み立てられます。照合と再利用は0.18で実装し、0.19に同梱しました。
2. **必要な原文を読む。** 0.19では、今回の依頼・会話・知識をまとめて読み、出典や記事の版を保って判断と観察を保存できるようになりました。人とAIの発言を分け、不完全な資料は不足を示します。0.20では、長い記事も関係する原文を版・位置付きで受け取り、条件や例外が読み取れない時に全文を追加取得できます。
3. **途中で分かったことを加える。** 0.20では、検索・作業案の照合・手順の再利用を、同じ作業の記録へ追加できます。先に読んだ記事や引用元を保ちながら、実際に判断へ使った発見を記録します。保存の一部が失敗した時も、成功した分を重ねずに再送できます。
4. **実行結果を次の仕事へ戻す。** 使った手順に、実行した条件・行動・失敗・修正・報告結果を、検証記録などの出典と結び付けます。次回の再利用では、過去の結果と今回の条件を比べられます。手順の記事が更新されていれば、過去に使った版から変わったことも示します。

たとえば、前回のリリースで「更新後に知識と出典が残っていることを確かめた」という検証があれば、次回はその条件と結果を手順と一緒に読み、今回も何を確かめるか考えられます。前回とOSや更新元の版が違えば、その違いを踏まえて確かめ直します。過去の成功をそのまま今回の成功と見なすものではありません。

こうして残す実行報告は、エージェントが検討する証拠です。報告を保存しただけで成功の正解や人の答えを作ることはなく、判断精度や長期的な効果の改善を示す実測値とも分けます。

### 0.21では、現在の内容と反例を手順の改善へつなぐ

同じ記事の現在の条件と過去の経緯は、エージェントが原資料を読んで分類した引用として分けて返します。未分類の範囲や前提変更は隠しません。作業案の照合では、分類した反例と失敗結果を別に探し、当時の条件・出典を今回の案と比べます。失敗後の修正を記録した時は、次回の再利用を待たず、元の原文と修正候補を手順の見直しへ返します。エージェントが証拠を確かめて更新し、人の追加採点は増やしません。分類や見直しも仮説であり、日付だけで正しさを決めたり、結果を自動で成功の正解にしたりはしません。

### 0.22では、経験をつないで、確かめて、手順へ育てる

複数の記事の原文と条件を結んだ見立てに、小さく確かめる方法と観察結果を残せます。役立った工夫は、その条件・避け方・確かめ方と一緒に、次のエージェントが受け取れる作業の手順へ育てます。元の出典と版を保ち、結果を人の正解にはしません。

知識が長くなった時は、分割・統合の案を確かめ、行き先を保存してから元記事を編集します。共有して読めることに加え、後の仕事で使い、確かめ、直せることを目指します。操作と制限は[ガイド](guide.ja.md)にあります。

### 0.23では、実際の仕事を通じて集合知を育てる

共有メモリーがあれば、複数のエージェントが以前の文脈を読めます。shikiiはさらに、一人の発見を仲間へ届け、別の条件で確かめ、同じプロジェクトの知識へ戻す流れをつなぎます。

1. **仲間の変更を受け取る。** 実際に供給された記事の版と現在版を比べ、前提や出典の変更を読みます。確認した記録と、判断に役立った証拠は分けます。
2. **証拠を照合する。** 明示した支持・反例・異なる手順の報告を、原文・条件・出典と共に読みます。共通の出典を示し、出典IDの違いや多数決だけで正しいとはしません。
3. **問いを次の仕事へ持ち越す。** 保存した問いは別の関係する仕事へ届きます。依頼の範囲内で小さく確かめ、以前の観察と条件を残して、同じ問いへ結果を足します。
4. **知識を一緒に直す。** 元の記事・現在版・提案を保存せずに比べます。重ならない変更は統合案にでき、競合は明示して残します。保存時にも現在の版を確かめ、さらに入った編集を黙って上書きしません。

例えば、CSVの道具を作るエージェントが区切り文字の条件に気づき、問いを残します。別のエージェントが別の合成入力で確かめ、一致した例と未確認の前提を記録します。最初の観察も保持し、次の仕事は記事の変更と限界を読めます。同じ説明を繰り返した回数を裏付けにせず、別の仕事を通じて知識を育てます。

これは集合知のための作業の流れであり、長期的な改善を測定したという主張ではありません。確認・実利用・観察報告・人の答えを分けます。モデルの重みは変えず、保存した問いで実験の許可を与えません。[使い方と上限](guide.ja.md#変更を受け渡し並行した仕事を比べる0230)を参照してください。

### 0.24では、担当者が入れ替わっても工程を通して知識を渡す

ホストから任意の担当割り当てを渡すと、調査・分割・実装・監査ごとの文脈で知識を準備できる。次の担当者は、それまでの調査範囲、未確認の問い、実際に読んだ記事版を現在の条件と比べる。実装の報告にはコードの版と統合状態を残す。食い違いは見分けるための小さい問いと方法へ、確かめた失敗は同じ手順の訂正へ戻せる。

たとえば、調査担当が「小さい入力は通ったが、大きい入力は未確認」と残す。実装担当はその条件と実装版を報告し、監査担当は反対の結果と小さい比較方法を加える。次の担当者には、単独の要約だけでなく、この条件と変更を渡せる。shikiiが証拠を保持し、何を実行して統合するかはホストが管理する。外部のホストを使わない利用者は、従来のまま利用できる。[接続の契約](guide.ja.md#外部の担当割り当てとつなぐ)を参照する。

この版で加わったのは外部ホスト向けの共通APIです。担当の条件と実装状態を渡す仕組みと、次の0.25で説明するchitenからの実利用・実行結果の報告を区別します。担当ごとの文脈は、同じプロジェクト内で必要な証拠を選ぶためのもので、アクセス権限の境界ではありません。

### 0.25では、今回の条件で経験を選び、実利用と結果を戻す

前回の手順を覚えていても、今回とOS・入力形式・実装版が違えば、同じ結果になるとは限りません。0.25では、単に直近の報告を読む代わりに、今回の依頼と条件に出てくる語を、過去の実行条件、次に行動・失敗・修正と比べて候補を選びます。手順ごとに最大2件を返し、同点なら新しい順にします。条件の語に一致がある時は、最上位と同じ一致数を持つ以前の失敗も残せます。

候補の順位は、実際の条件が一致するという判定ではありません。エージェントは元の条件・出典・不明点を読み、記事の版が変わっていれば確かめ直します。報告や検証資料が付いているだけで、今回も成功すると扱うものでもありません。

対応したchitenと接続すると、担当の報告から「記事を読んだ」「その知識が判断を変えた」「手順を実際に実行した」を区別してshikiiへ戻せます。実利用には判断への寄与と証拠を、実行結果には今回の条件・行動・失敗・修正・結果と出典を残します。報告を保存しても、実際に役立ったことや成功、人の正解を自動で確定しません。

たとえば、Linuxで確認したCSVの手順を、次の担当がmacOSの引用符付き入力へ適用するとします。過去の結果候補にLinuxの確認結果と、引用符を扱えなかった以前の失敗があれば、それぞれの条件を読んで、今回何を確かめるかを決めます。担当が実際に試した後で初めて、その入力・環境・観測結果を報告します。計画だけで終わった仕事には実行結果を作りません。次の担当は、その報告と出典を手順と共に読み、さらに違う条件を確かめられます。

chitenは別配布の任意の接続先です。chitenを使わないプロジェクトも、CLI・MCP・HTTPから知識の実利用や手順の結果を記録し、同じ条件付きの再利用を使えます。共有メモリーとの比較では、以前の文脈を読めることに加え、条件付きの経験を選び、仕事での利用と観察を出典へ戻す流れを説明しています。長期的な工数削減を実測したという意味ではありません。

### 0.25.1では、この使い分けをskillとMCPの案内へ揃える

0.25.1では、skillとMCPの説明を実際の動作に合わせて明確にしました。人の依頼・判断とエージェントの観測・検証をwikiの出典として区別し、過去の報告を今回の実行へ転記しないこと、閲覧や計画だけでは実行結果を作らないことを案内します。MCPの準備は検索・照合・再利用の一方式ずつとし、人の合意や未解決の選択と、未検証の実行結果を混ぜないよう欄の意味も説明します。保存形式と実行する操作は変えません。

修正した案内は、本体と導入済みskillを更新して使います。hookなしでMCPやskillを利用する場合は、本体の更新後に初期化済みプロジェクトで`shikii --init`を再実行すると、既存データとhook無効の状態を保ってskillを更新できます。その後セッション・画面・MCPを再起動します。[更新方法](guide.ja.md)も参照してください。

### 0.26では、仕事の中で判断を見直し、保存まで確かめる

知識を覚えて次に渡すことに加え、0.26では今回の仕事で何を見落としそうかを考え、分かった条件から次の行動を見直し、確かめた結果を残す流れを必須にします。依頼のhookが対象ターンを保持し、着手時の短い判断と終了時の確認を、依頼・記事の版・観察の出典へ結び付けます。途中で前提や行動が変わったら判断を更新します。

たとえば、以前のCSV手順に所有者の条件が書かれていれば、着手時にその条件を確認します。引用符付きの入力で別の問題が分かったら、次に確かめる対象を見直します。終了時は実際に確認した結果と未確認の条件を残し、次の仕事がその出典を読めるようにします。方針を維持する判断も有効で、新しい発見や記事を毎回作る必要はありません。

終了のhookは必要な記録の保存を確認します。訂正や観察の保存に失敗した項目は、別の保存成功や再準備では解消されません。古い終了記録を再送しても新しい証拠を確認したことにはならず、記事が変われば現在の版を読み直します。 必要な保存の残件が減れば復旧を続け、再試行しても保存が進まなければ未完了として止めます。

ここで増えるのは、今回の条件に結び付いた見直しと保存確認です。内部の思考の逐語記録を要求せず、判断の質や長期的な改善を証明するものでもありません。実際に見落としを防げたかは、後の仕事の証拠で確かめます。モデルの重みは変更せず、新しいモデルや利用者の採点も増やしません。[入力と復旧の方法](../skills/shikii/references/recording.md#required-review-while-doing-the-work)を参照してください。

### 0.27では、見立てを確かめ、次の確認を選ぶ

- 許可された確認の前に、期待する観察・条件・方法・結果で変わる判断を保存。実際の結果を同じ不変の試行へ結び、期待と異なる結果を引用して判断を更新します。
- 現在の出典が有効な小さい確認を選びます。同じ課題・問い・条件・方法・期待の実行2件を、同じ測定項目の前後と差で比較できます。
- 読む量を調整しても、必須の見直しと版固定の全文回復は維持します。未解決の判断、未保存の作業、前提変更があれば深く読みます。
- Claude CodeのBashで観測する対応した公開呼び出しの前に、有効なguardを確認します。Codexは終了時の確認、OpenCodeは自動hook無しのMCPとskillを使います。
- 判断・失敗理由は、条件と出典を保つ短い箇条書きへ。報告や測定の差はエージェントの証拠で、人の正解やモデルの重みの変更にはしません。

文脈を次へ渡すことに加え、観察から次に確かめる対象を変える流れです。計画の保存だけで実験は実行されず、同条件の値にも解釈が必要です。[手順と上限](../skills/shikii/references/recording.md#expectations-execution-and-the-next-check-0270)を参照してください。

### 0.28では、読む深さを実結果から選ぶ

以前の知識を引き継ぐことに加え、**その知識をどれだけ読めば今回の仕事に足りるか**を、実際の配送量と出典付きの確認結果から選びます。0.27で選べた読む深さに、別の仕事から得た経験を戻す仕組みです。

1. **実際の量を測る。** 渡した知識のJSONのUTF-8バイト数、読取回数、原文を追加で回復した回数を記録します。最初の抜粋だけで比べず、後から読んだ原文も含めます。
2. **同じ課題で比べる。** 標準の読み方である`focused`と、別の深さを比べます。記事の版・話題・担当の工程・確認する観点を揃え、必要な条件を読み取れたかを証拠と共に報告します。標準では不足した条件を、深い読み方で回復できた比較も候補になります。
3. **別の仕事でも確かめる。** 1課題の比較は候補です。別の2課題で、仕事と報告した実結果が重ならない比較が支持すると、同じ条件の次の仕事へ既定として反映できます。出典ID・来歴やJSONのキー順・同じ数値の表記だけを変えても支持は増やしません。
4. **不足を戻す。** 条件の見落としが報告された読み方は採用を止めます。後の成功だけでその不足を消さず、別の検証済み候補を選ぶか、詳しい確認へ戻します。記事版・話題・工程が変われば、以前の採用をそのまま引き継ぎません。

たとえば、更新後もデータを残すための長い手順を使う場面です。短い抜粋で始めても、復旧の条件が足りず全文を読み直したなら、その追加分も計測します。最初に短く渡しただけでは改善と数えません。別の仕事でも必要な条件を読み取れ、標準より配送量が少なかった比較が支持すれば、次の担当も同じ条件でその読み方を使えます。そこで新しい不足が分かれば、採用を止めて確認し直します。

明示した読む深さ、未解決の条件や前提変更に応じた詳しい読取、必須の見直し、版を指定した全文回復を優先します。品質確認は任意です。chiten 0.9.3以降では通常の相談報告と一緒に返せ、chitenなしでもCLI・MCP・HTTPの共通の仕組みを使えます。

学習するのはプロジェクトで知識を渡す方法です。モデルの重みや判断権限は変えません。測定対象は知識の配送量と読取であり、モデル全体のトークン数・呼出し回数・応答時間や回答品質が一般に改善したという測定ではありません。「2課題」は採用の固定条件で、統計的な独立性の証明でもありません。[入力と制約](../skills/shikii/references/recording.md#learn-a-reading-preference-from-checked-tasks)を参照してください。

### 0.29では、調査手順を改善する循環をつなぐ

0.29では、記憶した内容を今回どう使うかに加え、**繰り返し調査を減らす進め方を、実際の確認結果で選ぶ循環**を組み込みます。

1. **候補を作る。** 同じ調査が続いて進展しない時に、方法を変える案内のタイミングや短さを調整する候補を作ります。
2. **別課題で確かめる。** 候補を作る元になった課題を除き、エージェントが実際に確認した結果と証拠、案内に使ったデータ量を集めます。
3. **条件が揃えば採用する。** 初回は異なる2課題で必要な品質を確認し、案内量も減った候補を、同じ条件での次の手順にします。
4. **悪化したら戻す。** 必要な条件の見落とし、案内量の増加、支持する出典の不足があれば、候補を退けるか、採用前の手順へ戻します。失敗した候補は繰り返さず、次の別候補にはより多い確認を求めます。

たとえばCSVの不具合調査で、同じ仕様記事を何度検索しても確認結果が変わらないとします。shikiiは「別の確認方法へ移るよう早めに案内する」候補を作れます。別のCSV課題でも必要な条件を確認でき、案内量が減ったことが報告されれば採用へ進みます。その後に条件の見落としが報告されれば、以前の手順へ戻します。以前の助言を思い出すことに、別課題での検証と取り消しをつなげます。

通常は開始の`prepare`と終了の`record`の2回で記録します。「何が変わったか・何を根拠に確認したか・何が残るか」を一度送り、品質を実際に確認した場合だけ任意の`result.sufficient`を添えて、同じ証拠を共用できます。新しい知見のない会話では、長い振り返りやwiki記事を作る必要はありません。原資料の追加読取や途中の重要な訂正は、必要な時に別途記録できます。

品質不明は不明のまま扱います。空の結果や評価に使えない結果は支持へ数えず、原記録を保存して未確認と明示し、保存の再試行を繰り返しません。同じ実行の結果と読取確認は、確認項目・品質・証拠を合わせて確かめてから支持へ数えます。同じ証拠の別名を別の確認例にせず、証拠の対応はセッション期限後も原資料から辿れます。

候補が変えられるのは固定された案内手順の範囲です。必須の確認・原資料の回復・評価の規則・操作許可は変更できず、探索と保存量にも上限があります。改善するのはプロジェクトの手順の選び方で、モデルの再訓練や任意のコード変更ではありません。案内量の減少を、一般的な応答時間・モデルのトークン数・回答品質の改善率には置き換えません。詳しくは[記録の手順](../skills/shikii/references/recording.md#automatic-improvement-of-loop-procedures)を参照してください。

### 0.28.1〜0.29.2では、読んだ内容を保って再読を減らす

0.28.1では、MCPで繰り返す長い文を原文のまま共用し、元の位置を残します。完全なJSONも保持するため、表示を短くしたことを原資料の削除とは扱いません。0.29.1では、同じ作業で読んだ同一の抜粋を再利用します。省略した本文まで読んだことにはせず、条件の変更や明示した全文取得を優先します。

0.29.2では、同じ応答の案内を共用し、最終的に返した引用と抜粋だけを配送済みとして残します。関連記事の内容と証拠が完全に同じで、版の履歴だけが違う場合は以前の確認を使えます。編集した記事そのもの、新しい証拠、変わった前提の確認は省きません。

記憶の方針が変わった後の整理も、この版では通常は1依頼で最大2記事の1組ずつ進めます(のちの版で、1組は最大10記事に増えました)。中断しても保存した進捗から再開でき、明示して整理の完了を依頼した場合は続きも処理できます。好み・元の出典・過去の判断は残し、出典を読めない部分を確認済みにしません。

### 0.29.3では、今回の意図を保って配送の重複を減らす

この版では、知識を保存して次に使う流れへ、今回の依頼を保ったまま読む負担を下げる扱いを加えました。たとえば「所有者の条件を保ち、公開はせず、未決の選択は残す」という依頼なら、その本文と出所は応答の量を減らす時も保持します。上限へ収まらない場合は、依頼を黙って省かず保存前にエラーを返します。

同じ作業ですでに渡した記事の要約・適用条件・現在と過去の解釈が変わらなければ、以前の配送を参照して再利用できます。参照化では未分類の部分、再確認が必要な内容、反例、不足状態を残します。条件や出典の版が変わった場合や、全文取得を明示した場合は再利用で省かずに返します。応答全体の上限によって本文や説明が省略された場合は未読・未解決のまま扱い、十分な予算または個別の同版問い合わせで回復します。以前の応答を参照できない時も、この方法で原文を読めます。

ここで加わるのは、保存した知識を今回の条件に沿って渡す時の負担の制御です。人の目的や合意を自動で要約・推測せず、元の依頼と条件への参照を残します。応答全体が小さくなる場合だけ適用し、追加のモデルや設定を求めません。配送量の削減と、実際の判断品質や総作業時間の改善は分けて確かめます。[入力と参照の契約](../skills/shikii/references/recording.md#bounded-reading-and-memory-upgrades)を参照してください。

### 0.30.0では、保存した知識を読む処理も軽くする

shikiiの実行中は、上限を決めて記事の解析結果を再利用できます。再利用前に現在のファイルの全バイトを読み、出典と監視する前提を確認し、保存前にも再検証します。本文は共有し、変更可能なメタデータは呼出しごとにコピーするため、依頼・証拠・未決の条件を短くせずに複製の負担を減らせます。

この一時キャッシュはプロセスの終了で消えます。プロジェクトに残る知識は出典付きのwikiであり、振り返りや原文回復の条件も保ちます。

同じ操作内では、原資料の復号、会話履歴の集計、内容が完全一致する応答の計測も共用できます。抜粋を返せない時の解析や、通常検索で問い合わせに含まれない語の保持も省きます。元の依頼、検索順位、原資料の完全な回復、保存前の変更検出は保持します。操作内の処理を再利用しても、プロジェクトに残す知識を要約したり置き換えたりはしません。

同じ検索で同点の記事の順がぶれることも防ぎます。語の重みや配送の条件は変えません。

### 0.30.1では、全文回復を保って同じ説明を共用する

MCPの共通手順は`shikii_wiki`の説明へ全文を残します。初期化の案内は、ツールを使う前にそこを読むよう伝え、すぐに必要な規則も保持します。サーバーの案内を各ツールへ付加するクライアントで、同じ共通手順の全文が繰り返される量を減らします。

同じ作業ですべての記事を再利用でき、固定の`collective.notice`が変わらず、輸送全体が小さくなる場合だけ、以前の配送へ説明を結びます。変更・対比・調査・不足と回復先は残します。以前の応答を読めなければ、同じreceiptとqueryへ`reasoning:{depth:focused}`を付けて準備し直すと全文を読めます。明示的な出典回復や新しいreceiptでも全文を返します。

プログラムで扱う時は`structuredContent`を読み、エラー状態や追加の内容を保持できます。AIへは完全な結果を1回渡す手順を案内し、サーバーの両形式は残します。依頼や証拠を要約せず、表示の重複を減らす変更です。全値の保持と配送量、実モデルの判断品質は別に確かめます。[MCPの知識配送](mcp-knowledge.ja.md)を参照してください。

### 0.30.2では、中断した記録も次の仕事へ残す

記憶を次に使うには、書込みの途中で失敗しても、次に保存する完全な行を読める必要があります。0.30.2では、途中で切れた末尾と次の行を分け、追記の一部が失敗した時は可能なら元へ戻します。戻せなかった場合も、そのエラーを隠さず、次に成功した追記を読めるようにします。結果ラベルの重複確認と追記は同じ錠の中で行います。

画面で最後の問いに答えた時も、元の問いとカードへ結果を反映し、別の問いの件数を書き換えないようにします。失敗の回復と回答の対応を保つ改善であり、保存に失敗した結果やエージェントの報告を、人の正解として作り直すものではありません。

### 0.30.3では、worktreeの経験も同じプロジェクトに残す

専用worktreeはコードの作業場所です。wikiと共有作業記録は元プロジェクトに保持し、作業場所ごとに別の知識の履歴を作りません。報告にはworktree・ブランチ・検証したcommit・共有する証拠の場所を書きます。既存のプロジェクトの記憶をどこへ残すかを明確にする変更であり、AI本体の重みや学習に必要な証拠の条件は変えません。

### 0.30.4では、証拠を保って表示と読取を軽くする

たとえば、同じ状態表示で複数の判断の件数を出す場合、ラベルを毎回集計し直す代わりに、その1回の要求の中で結果を共用します。人のラベルの優先、入力ごとの最新の結果、しきい値ごとの数え方、採用しない結果の来歴は保持します。別の要求へ古い集計を持ち越す変更ではありません。

長い原資料を分割して読む時は、応答量の測定用に不要な複製を残さず、予算に近い長さから収まる部分を探します。最終的なホスト応答でも上限を確かめ、UTF-8の原文、位置、続きの検査を保ちます。途中で原資料や依頼の条件が変われば、従来どおり回復を拒否します。

最新の一定件数だけ読む履歴では、その件数の候補だけを保持します。全履歴の走査と復号は続け、時刻が同じ行の順や不正な行の扱いは変えません。全件が指定件数に収まる小さい履歴は、そのまま並べます。ここで減るのは表示・配送・履歴読取の重複処理です。プロジェクトの記憶や証拠を減らすものではなく、モデルの重み、学習の採用条件、判断を任せる範囲も変えません。

### 0.30.7では、役に立たなかった過去の回答を示さない

shikii は、似た依頼にあなたが前に答えた内容を、エージェントへ参考として示します。けれど、示しても一度も役に立たない回答は、毎回エージェントの読む量を増やし、本当に役立つ教訓の場所を奪います。

0.30.7 では、エージェントの振り返りで 2 回以上「使われなかった」と評価され、一度も役に立っていない回答を、以後は示さないようにしました。その回答は画面の「回答済み」から外し、知識欄の「AI が無効と判断した過去の答え」に並べます。回答そのものは正解として残り、判断の線を引く材料にも使われ続けます。プロジェクト全体で過去の回答が 10 回使われず、一度も役に立っていなければ、過去の回答を示すこと自体をやめます。

決めるのは AI の振り返りですが、その判断が合っているとは限りません。そのため次の 0.30.8 で、人が取り消せるようにしました。

### 0.30.8では、AI の判断を人が取り消せるようにする

0.30.7 で AI が「役に立たない」と判断した回答と、過去の回答を示すのをやめた判断は、画面の知識欄の「元に戻す」で取り消せます。取り消すと、それまでの評価は数えず、取り消した後に示した回数だけで改めて判断します。あなたの回答そのものには触れません。AI が決め、人はそれを元に戻せる、という分担です。

同じ版で、止める検査がエージェントの書いた行とあなたの書きかけを見分けるようにしました。依頼の前に書いていて、まだコミットしていない行は、エージェントの行として扱いません。一方、検査が一度止めたエージェントの行は、消すかコミットするまで覚えておき、次の作業でも止めます。記憶そのものの話ではありませんが、「誰がその行を書いたか」を作業をまたいで正しく持ち越すための変更です。

### 0.31.0では、記憶を呼ぶ側の失敗を減らす

ここまでの版は、何を覚え、何を届けるかを育ててきました。0.31.0 は、エージェントがその記憶を呼ぶ時の失敗を調べて減らした版です。この機械の会話の記録を数えると、エージェントはヘルプを求めて 1 行の使い方だけを返され、長い返事を道具に途中で切られ、断られても次に何を送ればよいか分からずにいました。記憶が育っていても、呼ぶたびに失敗していては使われません。

そこで、ヘルプはそのまま実行できる形を返し、断りは原因と次に送る内容を返し、返事はエージェントの道具が表示できる大きさに収めました。収まらない時も、検索の候補の上位や教訓の題のように、次の一手に要る物を残します。

もう 1 つは、作業の途中であなたが発言した時です。それまでは新しい依頼として準備をやり直し、エージェントは同じ記事を読み直していました。0.31.0 では、読んだ記事と保存した資料を次の準備が引き継ぎます。引き継ぐのは参照だけで、結果の報告は新しい依頼のものとして書きます。

直した前後は、本物のエージェントに同じ小さな依頼を流して比べました。数回ずつの計測なので、どの依頼でも同じだけ減るとは言えません。

### 0.32.0では、記憶の書き方を確かめ、記録の手間を減らす

「shikiiを整理して」と頼むと、エージェントが既存の記事を原資料と照らします。条件・例外・不明点・履歴を保ち、裏付けのない言い方や同じ意味の反復を修正する手順です。長さを品質の目標にせず、結果が書かれていないことを、実施していないという主張に変えないようにします。

新しい主張や変更した主張も、保存前に元の依頼と出典を確認します。解釈・翻訳・複数の資料をまとめた内容は、利用可能なら別担当が照合し、skillの条件を満たす原文転記は担当者が確認できます。独立した照合が使えなかった場合は、その未完了を残します。エージェントの行動を導く手順であり、生成した文章すべての品質を保証するものではありません。

依頼hookは準備済みの文脈を直接届けます。記事を編集した後は、保存された本文と出典への参照を返し、保存成功と確認完了を分けて示します。エージェントによる内容確認と、その確認の記録は残します。保存した知識の出典と履歴も保持します。

### 0.33.0では、エージェントが読む量を減らす

0.31.0 と 0.32.0 は、エージェントが記憶を呼ぶ時の失敗と、記録の手間を減らしました。0.33.0 は、その前にエージェントが読む量を調べた版です。この機械の会話の記録を数えると、エージェントは作業の始めに記録の手引きを丸ごと読み、MCP の道具の説明も会話のたびに大きな量を占めていました。Codex と OpenCode は、この説明を会話のたびに全部受け取ります。

そこで、作法と準備の返答は長い参照の節を示し、節だけを読む方法を作法に書きました。MCP の道具の説明からは、ほとんど呼ばれていなかった操作を外し、何か所にもあった同じ説明を 1 か所にまとめました。外した操作は CLI で使え、MCP で呼ぶと代わりの使い方を返します。

直した後に、Claude Code・Codex・OpenCode へ同じ小さな依頼を 1 回ずつ流しました。3 つとも作業を終え、記録の手引きを丸ごと読みませんでした。1 回ずつなので、実行ごとの揺れによる差とは分けていません。

### 0.34.0では、OpenCode でも hook が働く

これまで OpenCode は MCP の設定だけで、依頼の前に教訓を届けることも、作業の終わりに記録を促すこともできませんでした。OpenCode 2.x はプラグインが会話の動きを受け取れるので、shikii はプラグインを入れて、Claude Code や Codex と同じ hook を動かします。

OpenCode は 1 つのサーバーで複数のプロジェクトの会話を扱い、その知らせはどのプロジェクトのプラグインにも届きます。そのため、各会話の hook はその会話のプロジェクトでだけ動かし、作業の終わりの確認は 1 回の作業に 1 回にしました。プラグインは独立した監査を 5 回受け、実際の OpenCode 2.3.0 でも確かめました。作業の途中で会話を別のプロジェクトへ移した時など、教訓が届かない場面は連携の文書に書いています。

### 0.35.0では、記憶の更新で読めないページを飛ばせ、問いの答えが三つになる

記憶の更新は古いページを 1 回に少しずつ見直します。

記憶の最適化を頼むと、宣言して飛ばしていたページも含めて全部を見直し直します。普通の記憶の更新は、飛ばしたページを見直しに戻しません。

「では開始しましょう」などの開始の合図は、整理が前の依頼の続きと答えた時(`continues_previous`)に、新しい依頼でなく前の依頼への返事として数えます。その時は言い方に関係なく、この問いは出ません。整理が来るまでは、決まった相づちの一覧(ackReplies)が短い返事を前の依頼へ仮につなぎ、後は整理が決めます。

「始める前に確認してほしかったか」の問いは、本人が何を望んだかを聞く文です。答えは「確認してほしかった」「確認なしで進めてよかった」「問いに当たらない」の三つになりました。新しく作るプロジェクトには新しい文言が届き、`.shikii/decisions/` の写しが 0.9.2 から 0.34.0 まで（0.34.1 の開発版を含む）の内蔵文のままで、直した所も人が足したコメントも無ければ、次の更新で新しい文言になります。直した写し・コメントを足した写しは古い文言のまま残り、読めない・書けない写しも残して次の時に試し直します。すでに保存された答えは変換せず、この問いの較正はやり直しになります。

### 0.36.0では、教訓を使った本人がその教訓を評価する

shikii は、届けた教訓が使われたかを尋ねます。その答えで、同じ教訓をまた届けるか、記事を見直しに戻すかが決まります。この版までは、分かるはずのない相手が答えることがよくありました。サブエージェントに届いた教訓は親が評価していましたが、親に見えるのはサブエージェントの報告だけです。あるセッションに届いた教訓が、別のセッションの振り返りに並ぶこともありました。145 記事のあるプロジェクトでは、サブエージェントに届いた教訓の評価の半分以上が「分からない」でした。

この版から、サブエージェントは最後の報告の末尾に、届いた教訓ごとの 1 行を書きます。教訓を受けて何をしたか、または使わなかったことを書き、shikii がその行を保存します。shikii はサブエージェントを止めず、報告も書き換えません。親にはその教訓について尋ねなくなり、各セッションには自分に届いた教訓だけを尋ねます。教訓どおりに作業したものの、教訓のおかげかは分からない時は、そのことを評価に書けます。その配送は、教訓が場面に合っていた例として数えます。

Codex にも、Claude Code にあった動きが入りました。コマンドとファイルの直前の教訓、コマンドを実行の前に断る検査、サブエージェント自身の評価です。Codex のサブエージェントには、課題に合わせて選んだ教訓は届きません(Codex では、hook から課題の文を読めないためです)。届くのは、いつもの決まり、報告の書き方、コマンドとファイルの直前の教訓です。

本物のエージェントをサンドボックスで動かして確かめました。Codex では、サブエージェントがファイルを変える直前に教訓を受け取り、変更の結果と一緒に読み、教訓が求める確かめを変更の後に行って報告に書き、その行が保存されました。禁じたコマンドは実行の前に断られました。Claude Code では、サブエージェントが始まりに教訓を受け取り、使わなかったと報告し、その行が保存されました。OpenCode 2.x では、サブエージェントが始まりに教訓を受け取り、したことを報告し、その行が保存されました。どれも 1 回ずつなので、この流れが動くことは示せますが、モデルがその行をどのくらいの割合で書くかは示せません。

### 0.36.1では、届いた教訓をその依頼の中で評価する

この版まで、shikii は届けた教訓について、同じセッションの次の依頼の時に尋ねていました。1 つの依頼で終わったセッションには尋ねる機会がなく、そこで届いた教訓は評価されないまま残りました。依頼を 1 つ出し、作業が済んだら閉じる、というセッションは珍しくありません。

この版から、エージェントは作業を記録する時に、その依頼の中で教訓を評価します。作業を終えた直後なので、教訓を使ったかどうかを知っています。評価を書かずに作業を記録すると、shikii がその教訓を挙げ、あなたに答える前に評価するよう求めます。それでも評価しなかった分は、これまでどおり次の依頼の時に尋ねます。その依頼の中の評価は、あなたが作業に反応する前の評価なので、shikii は後から分けて数えられるように記録します。

本物のエージェントをサンドボックスで動かして確かめました。どれも依頼が 1 つだけのセッションで、課題は 1 つ、教訓も 1 つです。この版では、16 回中 16 回、評価が保存されました(Claude Code 6 回、Codex 6 回、OpenCode 4 回)。依頼と一緒に届いた教訓でも、ファイルを書き換える直前に届いた教訓でも同じでした。0.36.0 では 8 回中 0 回でした。この結果は、3 つのエージェントでこの流れが動くことを示します。ほかの課題、長い作業、教訓が何件も届く時の割合は示しません。

### 0.37.0では、プロジェクトの下の作業ツリーが、そのプロジェクトの記憶を使う

### 0.37.4では、worktree とサブモジュールでも場所を覚える

この版は、0.37.3 を広げたものです。shikii が教訓を保存し、届け、評価するしくみは変わっていません。0.37.3 は、`.git` がフォルダになっているふつうのリポジトリでだけ、覚えたリポジトリの場所を使っていました。作業ツリー(worktree)・サブモジュール・`--separate-git-dir` で git のフォルダを別の場所に置いたリポジトリでは、`.git` が git のフォルダを指すファイルなので、毎回 git に聞いていました。1 回の依頼で 4 回、ツールの呼び出しで 1 回、ターンの終わりで 4 回です。今は、ふつうのリポジトリと同じく、依頼で 3 回、ツールの呼び出しで 0 回、ターンの終わりで 3 回です。

hook は、git のフォルダを、ファイルから自分で見つけます。`.git` のファイルと、worktree では、その worktree を作った元のリポジトリと共有するフォルダを書いた `commondir` のファイルです。覚えた答えは、次のすべてが成り立つ間だけ使います。リポジトリの `config` ファイル(worktree では `config.worktree` も)が、git が答えた時と同じファイルであること(inode・大きさ・更新時刻・変更時刻が同じ)。見つけたフォルダが同じであること。設定が作業ツリーの場所を書いている時(`core.worktree`。サブモジュールが持っています)、その場所が、git が答えたフォルダのままであること。最後の確かめは、0.37.3 のふつうのリポジトリにあった問題も直しています。設定がリンクをたどって作業ツリーを指していて、後からリンクの向け先を変えると、最長 30 分、古いフォルダを使っていました。設定は、git 自身が書く形だけ読みます。引用符・次の行に続く値・2 つ目の値がある時は、git に任せます。覚える前に、ファイルから見つけた物(作業ツリーの一番上・objects のフォルダ・exclude のファイル・今のコミット)を git 自身の答えと比べ、同じ時だけ覚えます。そのため、読み違える配置があっても、間違った答えは出ず、git の起動が 1 回増えるだけです。リンクになっている `.git`・環境変数で選んだリポジトリ・ベアのリポジトリ・ファイルだけでは決められない配置は、今までどおり git に聞きます。worktree の今のコミットは、その worktree 自身の HEAD と、共有するフォルダの枝から読みます。reftable と、HEAD が worktree ごとの参照(`refs/worktree/`・`refs/bisect/`・`refs/rewritten/` の下)を指している時は、git に任せます。テストでは、worktree とサブモジュールでも今のコミットを git 自身の答えと比べ、これらの確かめも、ほとんどは外すとテストが落ちます。例外は 2 つです。設定ファイルの inode と大きさは、更新時刻と変更時刻が同じことを見ているので、外してもテストは落ちません。同じことを 2 重に守っている確かめ、たとえば見つけた git のフォルダと共有するフォルダは、両方を外した時だけ落ちます。

本物の Claude Code・Codex・OpenCode を、それぞれ worktree とサブモジュールで、git の呼び出しを数える代役を置いて動かしました。どれも、依頼で 3 回、ツールの呼び出しで 0 回(OpenCode にはツールの前の hook がありません)、ターンの終わりで 3 回 git を起動しました。6 回とも、この版のコードで動かしました。

### 0.38.0では、残ったことと、wiki に無かった話題を次の作業に渡す

この版は、作業の終わりに分かっていたことが、次の作業に届かずに消える所を 2 つふさぎました。1 つは、確かめきれずに残ったことです。もう 1 つは、wiki を探して見つからなかった話題です。

そこで、エージェントに新しい操作を求めるのをやめ、エージェントが今もう書いている `remaining` を、そのまま次の作業に渡すことにしました。次の作業の準備に届き、その作業が結果を記録すると閉じます。まだ残っている時は、受け取った作業が自分の `remaining` に書き直します。直した後は 6 回流しました。4 回は、残ったことが記録に残り、次のセッションに届き、次のセッションがその点を確かめて答えを出し(名簿に無い顧客が 1 件あること)、項目が閉じました。残りの 2 回は、届くのがエージェントの書いた文だけであることから来ています。1 回は、エージェントが残ったことを記録に書かなかったので、何も届きませんでした。もう 1 回は、残ったことを、ファイルの場所を確かめる、という趣旨の短い文だけで書いたので、次のセッションはファイルの場所を確かめただけで、名簿との突き合わせはしませんでした。エージェントが `coverage` に自分で書いた「確かめていない」範囲は、後の作業が同じ範囲を確かめたと書くまで閉じません。

wiki に無かった話題も、同じ経過でした。見つからなかった語を記録の返事に出し、「答えを見つけたなら短い覚え書きを足して」と書いても、エージェントは 12 回のうち 1 度も足しませんでした。ここでも、今もう書いている物を使いました。前の作業の結果の記録には、どこで答えを見つけたかが書いてあります。そこで、同じ語がまた見つからなかった時に、前に見つからなかった時に開いていた作業の記録を案内するようにしました(セッションが並んで動いている時は、検索した作業とは限りません)。直した後は、4 回とも、次のセッションがその記録を読み、「前の作業の報告では締め日は 25 日。ただし元の文書は今は無く、確かめられない」という趣旨で答えました(この試しでは、2 回目のセッションの前に元の文書を消しています)。案内するのは前の作業の報告で、確かめられた記事ではないので、この答え方は狙いどおりです。

この確かめの途中で、MCP の不具合が 1 つ見つかりました。コマンドの `shikii wiki query <id>` は保存済みの記録を返しますが、MCP の検索に同じ id を渡すと、言葉の検索になって何も返しませんでした。案内を受け取ったエージェントは 3 回とも MCP で読みに行き、3 回とも「中身が無い」と受け取っていました。id だけの検索の扱いを 1 か所に寄せ、コマンド・MCP・HTTP で同じにしました。本物の MCP の入口を通るテストも足しました。

確かめたのは Claude Code(sonnet)だけです。Codex と OpenCode では流していません。試した筋書きは、それぞれ 1 つです。wiki に無かった話題の試しでは、最初の依頼で「先に wiki を探し、無ければ文書を読む」と探し方を指定しています。次の作業に届くのは、エージェントが `remaining` に書いた文だけです。書かなければ届かず、短すぎれば、次の作業は何を確かめるのかを取り違えます。`remaining` から作った項目は、渡された作業が結果を記録した時に閉じます。受け取った作業が書き直さなければ、その先の作業には届きません。

### 0.39.0では、見つからなかった時の案内を、役に立つ時だけ出す

0.38.0 は、wiki で見つからなかった語を覚え、同じ語がまた見つからない時に、前の作業の記録を案内するようにしました。この版は、その案内が役に立つ条件から見直しました。

案内が役に立つのは、案内した記録に、検索した語の話が書いてある時です。0.38.0 は、語が見つからなかった時に開いていた作業の記録に結んでいました。作業の本筋と関係の無い語を検索して、結果に何も書かなかった作業にも結ばれるので、後の検索が、検索した語について何も書いていない記録に案内されました。最初は、どのセッションが検索したかを覚えて、結び先を絞る案を考えました。作業の準備に続けた検索はセッションが分かるので、セッションを覚えるようにしました。けれども `wiki query` はセッションを知りません。また、検索したセッションの記録に、検索した語の話が書いてあるとは限りません。結局、役に立つ条件を直接確かめることにしました。記録が語を結ぶのは、作業の結果の文が、検索した語で見つかる時だけです。決まりは wiki の言葉の検索と同じで、見るのはエージェントが書いた文だけです(欄の名前は数えません)。0.38.0 の確かめで本物のエージェントが残した結果 58 件に当てると、探した語と同じ話題の 32 件は全部が見つかり、別の話題の 26 件は 1 件も見つかりませんでした。

確かめたのは Claude Code(sonnet)だけで、筋書きは 1 つ、3 回ずつです。Codex と OpenCode では流していません。単独で見つかる語を知らせるのは、並べた語のどれかが記事にある時だけです(この筋書きでは「請求」が記事にありました)。言い換えた語がどれも記事に無い時は、今までどおり見つかりません。結ぶ条件を当てた 58 件は、どれも「締め日」の 1 語で当てた物です。

0.40.0 は、判断に答える AI を TypeSafe の Jev にするか手元のモデルにするかを、プロジェクトごとに選べるようにしました。chiten のような道具が「この一節は、この主張を支えるか」を聞く既製の問い quote-supports も足しました。

0.40.1 と 0.40.2 は、0.39.0 で残した事を直しました。0.39.0 は、作業の準備に続けた検索の語を、検索したセッションの記録だけに知らせるようにしましたが、`wiki query` はセッションを知らないままでした。調べると、エージェントはシェルのコマンドに、今のセッションの id を環境変数で渡していました(Claude Code は `CLAUDE_CODE_SESSION_ID`、Codex は `CODEX_THREAD_ID`、OpenCode は `OPENCODE_SESSION_ID`)。一方で、MCP のサーバーに残る id は起動した時の物で、今のセッションと違っていました。そこで、コマンドの `wiki query` だけが環境変数の id を使い、hook がそのプロジェクトで記録を残したセッションの id だけを採るようにしました。変数どうしが別のセッションを指す時は、推測を残さないため、どのセッションにも結びません。0.40.1 で Claude Code と Codex に、0.40.2 で OpenCode に対応しました。MCP と HTTP の API からの検索は、これまでどおりセッションを持ちません。

0.40.1 は、wiki の検索も速くしました。1 回の検索で、記事が引く出典を、出典ごとに 1 回だけ確かめます。合成した 300 件の wiki で、何も見つからない検索は約 98 ms から約 67 ms に、検索語を入れない一覧は約 124 ms から約 77 ms になりました。返事は変える前とバイト単位で同じです。古い記憶を wiki へ移す時に、エージェントが 1 回に見直す記事も、2 件から 10 件までにしました。

OpenCode は、本物の 2.3.2 で、コマンドに渡す変数と、hook が同じ id で記録を残すことを確かめました。OpenCode のモデルにコマンドを流させる通しの確かめは、モデルの提供元が混んでいて流せず、コマンドは自分で流しました。OpenCode のサブエージェントは自分のセッションで動き、hook はそのセッションの記録を残さないので、サブエージェントの中の検索はセッションを持たないと読んでいます(本物では流していません)。

### 0.41.0では、終わったセッションが残した記録を、人が確かめてから消す

0.40.2 の確かめで、本物の OpenCode をこのプロジェクトで流しました。その試しのセッションは、本物の記録として約 30 のファイルに残りました。セッションの作業状態、届いた教訓の配送と評価、原資料、判断と機械の正解、見残しの台帳、検査の記録などです。中身は実際に起きた事の正しい記録でしたが、試しの記録が後の作業の手がかりに混ざります。shikii には記録を消す操作が無く、記録どうしが id で引き合うので、手で消すと本物の記録を壊すおそれがありました。

そこで `shikii forget` を足しました。消す物は、セッションの id を持つ欄と、そのセッション自身の記録が持つ id をたどって決めます。id を文字として検索して消すことはしません。確かめると、文字の検索で見つかるのは消す物の半分に満たず、見つかった中には wiki の記事が引いている、消してはいけない原資料もありました。セッションの作業状態には、読んだだけの別の会話の原資料も載っています。そのため、そのセッションが作った物だけを消す側に入れ、読んだだけの物は残します。

消すのは人が決めることです。最初は MCP には載せず、人が端末で流す形にしました。その後、MCP からも、人に確かめてから消せるようにすることになりました。そのために MCP の elicitation を使います。shikii がエージェントを通さずに人へ直接「消していいですか」と聞き、人が「はい」を選んだ時だけ消します。エージェントが道具の引数で「はい」を渡しても消しません。人が決めている間に記録が変わった時は、何も消さずに止めます。

確かめたのは、テストの中で作ったプロジェクトと、このプロジェクトの試しの 4 セッションです。MCP の問いを本物の Claude Code・Codex・OpenCode に出させる確かめはしていません。Claude Code と Codex は、手元のプログラムの中身から対応していると読んでいます。OpenCode は分かりません。

その後の監査で、「まだ動いているか」の決め方を何度か直しました。最初は、最後の記録から 10 分たったかで決めていました。しかし長い作業では、10 分以上記録が書かれないことがあります。そこで、hook がエージェントのプロセスを覚え、そのプロセスが生きているかで決めるようにしました。アプリが開いたままでも、考えておらず、そのセッションが始めた物も動いていなければ消せます。ただ、考えていないことは hook の出来事から推し量るしかありません。裏のサブエージェントや、他の hook が続きを求めた時などを、監査のたびに 1 つずつ見つけて、消さない側に倒しました。

同じ版で、chiten のような道具が、自分の仕事から作った記事を取り下げる `shikii wiki withdraw` も入りました。初めは記事を消していました。しかし、出典の種類は控えた側が自由に書けるので、人の言葉から作った記事も取り下げられてしまいます。そこで、取り下げた記事は消さずに残し、人が答えのページで確かめてから、元に戻すか削除するかを選ぶ形にしました。

### 0.42.0では、1 日に 1 回、溜まった記憶をまとめて見直す

Claude Code には、溜まった記憶を裏でまとめ直す機能があります。shikii にも近い仕組みはありました。依頼ごとの振り返りで訂正を記事にし、記事の書き方の方針が変わった時は、既存の記事を少しずつ見直します。しかし、いつ見直すかを決めるきっかけがありませんでした。振り返りで拾い損ねた訂正を、あとから読み直すこともしていませんでした。

そこで、前回の知らせから 24 時間以上たち、その間に作業が 5 件以上終わった時に、セッションの始めにエージェントへ見直しを頼むようにしました。24 時間と 5 件は Claude Code の既定と同じです。名前は、Claude Code の機能と区別でき、親しみやすい `shikii nap`(記憶のひと休み)にしました。

shikii は見直す物を並べるだけで、記事は書き換えません。最初の形では、知らせを出した時刻で、読み直す会話の範囲を決めていました。そのため、エージェントが知らせを受けても見直さなかった間の会話が、次の範囲から落ちていました。今は `shikii nap` が実際に出した所までを覚え、次はその続きから出します。会話は古い方から 64 件ずつ出します。

軽くしつつ精度を落とさない工夫も 2 つ入れました。1 つは、会話ごとに、その会話を出典にしている記事の id を付けることです。エージェントは、記事になった会話を確かめるだけで済み、記事になっていない会話を重点的に読めます。もう 1 つは、記事が前提にしているファイルが変わった時に、その記事を先に示すことです。エージェントの返事を短く削る案も測りました。しかし、ほとんどの返事は 200 バイトに満たず、削ると人の返事が何への訂正か読めなくなるので、採りませんでした。

本物の Claude Code では、知らせを受けたエージェントが裏のサブエージェントで `shikii nap` を流し、まだ記事に無かった手順を 1 件足しました。すでに記事になっていた訂正は書き直しませんでした。Codex は、作業を頼む依頼では同じように見直しましたが、「今日はここまで」だけの依頼では見直さずに終わりました。OpenCode は、モデルの提供元の利用上限に当たり、確かめられていません。
