# shikii の構造（設計文書、2026-10-18）

ゴール: **人が出すのは意図と正解だけ。聞き方も信頼も段階も機械が育て、育った知識は人のあいだで共有される。**

この文書は、その目標を支える構造を 4 つの柱で書く。実装済みのものと、まだのものを分けて示す。数字は [bench.md](bench.md) と [operations.md](operations.md) を指す。

## 柱 1: 検証できる wiki（中心）

知識は文章ではなく**主張**として溜める。パターンのページは「主張 + 条件 + 証拠 + 再検証の手順」で、前書き（YAML）を機械が読み書きし、本文は人が書く。

- 主張（claim）: 一文。「素のチャット用モデルには plain 配置」
- 条件（applies_to）: 型、モデルの系統、言語など、効く範囲
- 証拠（evidence）: run ごとに 1 件。日付、モデル、数字、判定（supports / contradicts / inconclusive）
- 再検証の手順（retest）: どの spec で、どの候補がどれを上回れば支持か。`shikii wiki verify` がそれを今のモデルで回し、対の勝敗と片側の符号検定で判定して証拠を足す
- 状態（tentative / confirmed / rejected）を変えるのは人だけ。機械は「独立したモデル 2 つが支持し反証が無い」時に confirmable と言うだけ

これが文章の wiki（LLM が資料を編んで更新するもの）と違う点は、**知識が古くなれば自分で分かる**こと、そして**別の人が自分のモデルで同じ主張を回せば、その結果が証拠に加わる**こと。共有されるのは文章ではなく、再現できる観察。

機械の使い方: 提案役は今の型とモデルの系統に当てはまる主張だけを読んで候補を作る。`tune` の run はどの主張の証拠になるかを記録する。エージェントは run から主張を起草できるが、状態は変えない。

実装: `cmd/shikii/wiki.go`、`wiki/index.md` の形式、`wiki/patterns/plain-layout-for-small-chat-models.md` と `state-last-for-recurrent-readout.md` が最初の例。`tune` は run ごとに、有意に勝った候補を主張の下書き（`patterns/drafts/`）として起草し、既存の主張に証拠を足す（自動で育つ部分）。残り: 他のパターンに retest を付ける（noul の文言の主張は noul の spec に候補が要る）、提案役が主張の条件で読む範囲を絞る。

## 柱 2: 問いと正解は資産、モデルは使い捨て

知識を重みではなく**問いの側**（spec の文言・選択肢の説明・配置・分解・文脈・似た例の引き方・wiki の細則）と**正解の貯金**に置く。モデルを替えたら `calibrate` が貯金を聞き直して線を引き直すだけで、人の手は 0。

聞き方は 1 つの探索空間として扱う。次元は: 文言、選択肢の説明、入力の並べ方（template）、配置（layout）、分解（steps）、文脈の入力（state.context）、似た例の数と引き方。`tune` はこの空間の探索器で、採用の門は holdout と符号検定。候補は人か提案役が書くが、空間が定義されていれば「どの次元を動かすか」で候補を機械が作れる。

ベンチの裏付け（bench.md）: Qwen3-4B で、文言と配置を tune が選ぶと 0.903、似た例を足すと 0.952 で約 50 件の LoRA（0.952）に並ぶ。はい/いいえ の 32 件では約 26 件の LoRA が土台より悪く、似た例は効いた。**重みを触らずに微調整の正解率に届き、しかもモデルを跨いで持ち越せる**、が主張。

残り: モデル交換のベンチ（同じ spec と正解を 3 つのモデルに掛け、人の正解 0 件で線が戻ることを示す。LoRA はモデルごとに学習し直し）。似た例を引くことを tune の候補の次元にする（今は呼ぶ側が examples を作る）。入れ子の分割（外側で測り内側で選ぶ）と区間の表示。

## 柱 3: 信頼の負担を定義し、LLM に渡す

主張できるのは「この条件で測った精度」だけ。条件は 1 枚にまとめ、`check` がそのまま検査する。

- 線は（問いのハッシュ、モデル名）ごと。文言も配置も変われば線は消え、`act` は出ない
- 線を書く条件: 人（または結果）が決めた正解が `min_n` 以上。機械の正解（上の段の答え）だけでは引かない。正解には系譜（人 / 機械）があり、聞き直しで系譜は変わらない
- 抜き取り: `act` で自動で動いた判定の 20 件に 1 件を人に見せ、人の正解だけでの `act` の精度を測る。`check` はそれが `min_n` 以上あって精度を割れば落とす
- **決定ごとの領収書**（最初の版あり、`receipt`）: `act` の判定に、線の方法と引いた日、正解の数とそのうち人の分、人が確かめた act の判定の数と精度を添える。精度の区間の下限はまだ（次）。「95% の確信」ではなく「この種の判定は人が検査した n 件で精度の下限 x」と言える
- **審判（judge）**（最初の版あり、`shikii judge`。審判は今は spec の質問だけを読み、wiki の細則はまだ渡していない）: 別の（より大きい）モデルが wiki の細則（spec の Rules、確定した例）を読んで正解を出す。審判は先に人の正解で較正し、一致率が門に届く審判の正解だけを重み付きで使う。人の仕事は、全部に答えることから、審判を抜き取りで検査することに縮む。審判と判定モデルが同じ系統なら間違いが相関するので、`judge` は「判定モデルが外した例での一致率」も出す（門には使っていない。低ければ同系統の審判は穴を埋められない目安）。本文が外に出せない判定は審判も手元に限る

この 4 層（人 → 細則 → 審判 → 判定モデル）が回れば、人が出すのは意図と抜き取り分の正解だけになる。

## 柱 4: 段階は制約付き最適化

「精度 ≥ act を守りつつ、1000 判定あたりの人の判断を最小化」。段は 最小の質問 → 文脈を足す → 人。段を上げる条件は「迷い」（ask、多択では discard も）。各段は別のハッシュで別の線を持つ。上の段で確信した答えは下の段の正解になり（機械の正解、重みは確率）、人の答えは通った全部の段に付く。進み具合は `status` の「1000 判定あたりの人の判断」。

残り: 費用（呼び出し回数、文脈の長さ）を目的関数に入れ、段を上げる条件そのものを tune の対象にする。

## 再現性の約束

数字は全部スクリプトから出す（`scripts/bench/`）。run の記録（`wiki/runs/`。プロジェクトでは `.shikii/wiki/runs/`）は不変で、文書の数字は run を指す。run には変換役の版と配置を記録する（古い変換役が配置を無視して「同じ数字」を出した事故が 1 回ある）。テストは RED を示してから GREEN、安全に関わる分岐は変異で落ちるのを確かめる。

## 優先順位

1. 柱 1 を厚くする: 他のパターンに retest、提案役が主張の条件で読む、run から主張を起草
2. 柱 2 のベンチ: モデル交換、似た例を tune の次元に
3. 柱 3 の領収書と審判
4. 柱 4 の費用の目的関数
